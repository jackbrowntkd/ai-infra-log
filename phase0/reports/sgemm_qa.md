# SGEMM：从 naive 到寄存器分块 —— 实测报告

阶段 0 产出物（对应 `LEARNING_PATH.md` 的 C9）。
配套：`phase0/cuda/sgemm.cu`，原始输出 `phase0/reports/sgemm_ncu.txt`。

**设计**：N = 1024，A/B/C 各 4 MB（工作集 12 MB，远大于 1 MB 的 L2）。
三个版本逐步加手段，每步只改一件事。

## 一、结果

| 版本 | 手段 | 耗时 | GFLOP/s | 占峰值 | 相对 naive |
|---|---|---|---|---|---|
| `sgemm_naive` | 每线程 1 个 C 元素，k 循环直接读全局 | 10.970 ms | 195.8 | 7.1 % | 1.00x |
| `sgemm_tiled` | 32x32 共享内存分块 | 7.815 ms | 274.8 | 10.0 % | **1.40x** |
| `sgemm_reg` | 分块 + 每线程 4x4 寄存器分块 | **3.721 ms** | **577.1** | **20.9 %** | **2.95x** |
| `sgemm_reg2` | reg + 修访存模式 + 向量化（**照官方 rules 改**） | **2.036 ms** | **1054.5** | **38.2 %** | **5.23x** |

正确性：三个版本两两对拍，1048576 个元素全部一致（最大差 0）-> PASS。

## 二、最重要的发现：DRAM 从头到尾都不是瓶颈

ncu 逐版实测（**九个指标在同一次 ncu 调用里采，保证同源可比**）：

| 版本 | **DRAM** | **L2** | **L1TEX** | **SM** | LSU | FMA | 占用率 |
|---|---|---|---|---|---|---|---|
| naive | 9.33 % | **11.08 %** | **88.26 %** | 88.23 % | **87.43 %** | 21.92 % | 97.5 % |
| tiled | 10.45 % | **11.14 %** | 77.86 % | 65.67 % | 71.92 % | 13.89 % | 98.4 % |
| reg | 15.35 % | **16.24 %** | **97.26 %** | 27.76 % | 20.12 % | 28.35 % | 96.0 % |

**L2 吞吐从头到尾只有 11 ~ 16 %** —— 和 DRAM 一样，压根没参与竞争。
全场唯一接近饱和的是 **L1TEX（88 % / 78 % / 97 %）**。

> ⚠️ **测量口径提醒**：这几列必须**同一次 ncu 调用**采。分两次采同一指标会差 8 个点
> （实测：naive 的 `l1tex__throughput` 一次 88.26 %、另一次 79.99 %）。
> 原因见第七条末尾"回放让缓存变暖"。

**DRAM 利用率始终只有 11 ~ 12 %。** 原因是硬件缓存已经把复用接住了：

```text
如果完全不缓存，naive 要搬 8 x N^3 x 4 B = 8.6 GB
实测 DRAM 只搬了 163.5 MB（读）+ 29.6 MB（写）  ->  缓存接住了 98 %
```

（naive 的 L1 命中率 94.92 %，L2 命中率 60.32 %。）

### 所以"tiling 只快 1.40 倍"不是 tiling 失效，而是**它要解决的问题不存在**

标准叙事里，tiling 的收益来自"把每个元素的全局读取次数从 N 降到 N/TILE"，
从而省 DRAM 流量。但这里 DRAM 本来就没被吃满——**L1/L2 已经把复用做掉了**。

> **教训：杠杆表选手段之前，必须先确认瓶颈在哪一级。**
> tiling 属于"缩短复用距离"那一行；而这一版 naive 的真瓶颈是
> **"每个 FMA 要两次取数"**（L1TEX 88 % + SM 88 %），属于"指令/取数密度"那一行。

## 三、真正的杠杆：把"取数:FMA"从 2:1 降到 0.5:1

| 版本 | 每个 k 步 | 取数:FMA |
|---|---|---|
| naive / tiled | 2 次取数 + 1 次 FMA | **2 : 1** |
| reg(4x4) | 4+4 次共享内存取数 + **16 次 FMA** | **0.5 : 1** |

取数指令数降到 1/4，所以 SM 吞吐从 88 % 掉到 27.8 %，时间从 10.97 ms 降到 3.72 ms。

## 四、下一个瓶颈已经出现了

`sgemm_reg` 的 **L1TEX 97.30 %** —— 共享内存的取数带宽被打满了。

这就是经典 SGEMM 优化的下一步：**减少共享内存的取数次数**
（比如每线程算 8x8、或用更宽的向量化取数），而不是继续加 tiling。

> 瓶颈在三级之间搬家：**DRAM(12 %) -> L1TEX(88 %) -> L1TEX(97 %)**，
> 每一步都换了一个资源，方法也必须跟着换。这正是 `notes/09` 那张杠杆表的用法。

## 五、v3：照着官方 rules 改（2026-10-04）

官方规则的抽取已经脚本化（`phase0/ncu_rules.py`）：
`reports/sgemm_reg_rules.md`（改前）与 `reports/sgemm_reg2_rules.md`（改后）可直接对照。

**⚠️ 关于 `Est. Speedup` 的口径**：同一条规则在不同次采集里会波动——
`sgemm_reg` 的"全局 load 访存模式差"这一条，我手工采到 59.93 %，
脚本重采同一 kernel 是 74.28 %。所以它该读作**量级与排序信号**，
不是精确预测；**对比时要用同一批次的输出**。

前面几版都是我自己的分析。这一版**改成"读 ncu 的官方规则 + 照做"**，
结果比我自己推的快得多。

`ncu --set full` 对 `sgemm_reg` 给出的三条官方指路：

```text
OPT  Est. Speedup: 59.93%   全局 load 访存模式差：每线程只用 sector 的 7.1/32 字节
OPT  Est. Speedup: 57.79%   全局 store 同样差：8.0/32 字节
OPT  Est. Speedup: 48.19%   每个 warp 平均花 19.7 周期等 MIO 指令队列不满
```

按这三条做了三件事（`sgemm_reg2`）：

| 官方指路 | 我的修法 |
|---|---|
| 全局 load 跨行（warp 内 32 个线程读 32 行，步长 N） | 改索引映射：连续线程读连续的 k -> 合并 |
| 全局 store 按 tx*TN 跨步（stride = 4） | 改成 `float4` 一次写 16 B |
| MIO 队列堵（共享内存取数指令太多） | 共享内存取数也改成 `float4` |

### 结果：官方说 60 %，实际拿到 45 %

| 版本 | 时间 | GFLOP/s | 占峰值 |
|---|---|---|---|
| `sgemm_reg`（改前） | 3.696 ms | 581.0 | 21.1 % |
| **`sgemm_reg2`（改后）** | **2.036 ms** | **1054.5** | **38.2 %** |
| 提升 | **-45 %** | **+82 %** | |

正确性：与 naive 对拍 1048576 个元素，全一致 -> PASS。

### 官方指路的三条全部应验

| 指标 | reg | reg2 | 说明 |
|---|---|---|---|
| 全局 load/store 告警 | 有（59.9 % / 57.8 %） | **消失** | 合并访问修好了 |
| MIO stall 周期 | 19.7 | **7.1** | 队列压力降了 2/3 |
| 调度器发射间隔 | 5.3 周期 | **2.7 周期** | 发指令更密了 |
| `pipe_fma`（cycles 口径） | 28.4 % | **54.4 %** | **算力真正用起来了** |
| 占用率 | 96.0 % | **72.0 %** | 寄存器 64 -> 73，占用率降但更快 |

**注意最后两行**：占用率降了 24 个点，性能却涨了 82 % ——
又一次印证"**占用率不是目标**"。

**DRAM 吞吐从 15.4 % 涨到 22.0 %** 也不是"变差了"：分母（时间）变小了，
同样字节数除以更短时间 = 更高吞吐。**看吞吐百分比时永远要记住它是"字节/时间"。**

### v3 之后，官方指出了下一个瓶颈

```text
OPT  Est. Speedup: 31.53%       共享内存 store 有 1.5 路 bank conflict（524288 次）
OPT  Est. Local Speedup: 47.6%  每 2.7 周期才发一条指令
OPT  Est. Speedup: 44.78%       warp 仍在等 MIO 队列（7.1 周期）
```

**不是"把上一招再加强"，而是换了新目标**：共享内存 bank conflict。
瓶颈又一次搬家：从"全局访存模式"搬到"共享内存冲突"。

## 八、复盘：每一步的因果链（对照 `notes/09` 的五步循环）

### 补：`sm__throughput` 到底是啥（用这三个版本证明）

`sm__throughput` 的官方定义是 *"SM throughput assuming ideal load balancing across SMSPs"* ——
它是 **SM 内部最忙那条流水线**的利用率，**不是"算力利用率"，也不是占用率**。
钻到流水线一级看就一目了然：

| kernel | `sm__throughput` | **LSU（取数）** | **FMA（算力）** | L1TEX |
|---|---|---|---|---|
| naive | 88.23 % | **87.43 %** | 21.92 % | 88.26 % |
| tiled | 65.67 % | **71.92 %** | 13.89 % | 77.86 % |
| reg | 27.76 % | 20.12 % | **28.35 %** | **97.26 %** |

- **naive 的 "SM 88 %" 其实是 LSU 87 %**，FMA 只有 22 % —— 所以它算力只跑到峰值 7.1 %。
- **reg 把 LSU 压到 20 %**，FMA 升到 28 % 成为最忙的管道；但两者都没满，
  真正的天花板已经变成 **L1TEX 97.3 %**（共享内存取数带宽）。

### 还有一个反直觉的坑：ncu 的 Duration 对"吃缓存"的 kernel 不可靠

同一次 ncu 调用里的 Duration：naive **8.25 ms**、tiled **9.37 ms** ——
**看起来 tiled 更慢**。但独立运行是 naive 10.970 ms、tiled 7.815 ms，**tiled 快 1.40x**。

原因：ncu 会**回放**同一个 kernel，回放之间 A/B 矩阵留在 L2 里 -> **缓存变暖**。
对 naive 这种靠硬件缓存吃复用的实现，变暖等于开挂（8.25 < 10.97）；
对 tiled 影响小，于是两张表的结论**正好相反**。

> **所以：性能比较永远用独立运行的时间；ncu 只用来回答"哪个资源最忙"。**
> （这条比 `notes/08` 里"ncu 的 Duration 通常可信"要更严格——它只在
>  kernel 对缓存状态不敏感时成立。）

> 结论：`sm__throughput` 高有两种完全不同的含义（取数管道 vs FMA 管道），
> **必须再钻一层 `sm__inst_executed_pipe_*` 才能区分**。

| 步骤 | 测到什么 | 判断（落在杠杆表哪一行） | 做了什么 | 结果 |
|---|---|---|---|---|
| **0 基准** | — | — | 写最简单的**正确**实现（每线程 1 个 C 元素） | 10.970 ms，195.8 GFLOP/s（峰值 7.1 %） |
| **1 测量** | DRAM **12.2 %**、L1TEX **88.2 %**、SM **88.1 %**、L1 命中 94.9 % | **不是 DRAM 档**；真瓶颈是"取数/发射" | 什么都不改（先判断） | 推翻"tiling 会快 30 倍"的预期 |
| **2 第一次改** | 按**错误判断**（以为 DRAM 档）选了"缩短复用距离" | 杠杆表第 3 行（缩短复用距离） | 32x32 共享内存分块 | 1.40x；DRAM 反降到 11.4 %、L1TEX 76.7 % |
| **3 重新测 + 重新判断** | L1TEX 76.7 % 仍最高 | 真杠杆是**降低取数:FMA 比** | 4x4 寄存器分块（2:1 -> 0.5:1） | **2.95x**；SM 88 % -> 27.8 % |
| **4 再测** | L1TEX **97.3 %** | 共享内存取数带宽满了 | （下一步）每线程 8x8 + 向量化取数 | 未做，未收敛（20.9 % ≪ 90 %） |

### 三条方法论

**1. 每一步都由测量驱动，不是照抄教科书。**
naive 的直觉预期是"DRAM 瓶颈"（AI = 0.25，远在转折点左边），
但实测 DRAM 只有 12 %——**L1/L2 已经把复用接住了**（L1 命中 94.9 %）。
如果照抄教科书直接上 tiling，会得到 1.40x 就以为"优化到头了"。

**2. 判断错没关系，实验会纠正你——但前提是一次只改一个变量。**
第 2 步的 tiling 收益小，但它**没有掩盖问题**：DRAM 降到 11.4 %，
说明"省 DRAM 流量"这个方向确实用不上。于是第 3 步能干净地换杠杆。

**3. 瓶颈会在资源之间搬家。**

```text
DRAM 12 %  ->  L1TEX 88 %  ->  L1TEX 97 %
   (naive)      (tiled)         (reg)
       每一步都必须换方法，不能把上一招再加强
```

### 那教科书为什么第一课就教 tiling？

因为教科书默认的数据量大得多。本例 N = 1024（工作集 12 MB），
1 MB 的 L2 还能接住相当一部分复用；**N 一大，L2 就接不住了，DRAM 才会真的成为瓶颈**，
那时 tiling 的收益才会显现。

> 这正好接上 `LEARNING_PATH` 里那条结论：**数据量决定你在哪一档，档位决定手段。**
