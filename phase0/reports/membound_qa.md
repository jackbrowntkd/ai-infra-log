# Memory-bound 三问三答

配套实验：`phase0/cuda/membound_sweep.cu`，原始输出 `phase0/reports/membound_sweep.txt`。
所有变体的访存量恒为 720 MB，算术强度恒为 1/12 FLOP/byte。

## EXP1 向量宽度还有意义吗

| 变体 | block | 耗时 | 带宽 | 每线程字节 |
|---|---|---|---|---|
| f1 | 256 | 4.213 ms | 179.2 GB/s | 12 |
| f2 | 256 | 4.223 ms | 178.8 GB/s | 6 |
| f3 | 256 | 4.215 ms | 179.1 GB/s | 4 |
| f4 | 256 | 4.217 ms | 179.0 GB/s | 3 |

**四者完全一致，差异 0.25% 以内，在噪声里。**

反直觉的是 **float3 并不慢**。`float3` 是 12 字节、对齐只有 4 字节，
编译器生成不了单条 128 位访存，必须拆成 3 条 32 位加载。按"减少指令数"的
逻辑它应该最慢 —— 实测和 f4 一模一样。

原因：kernel 被 DRAM 卡死时，指令数根本不构成约束。SM 利用率只有 4.98%，
95% 的发射能力闲置，多出来的 load 指令被免费吸收。

决定带宽的只有两件事：

1. 总字节数
2. 访存是否 coalesced

float3 虽然指令多，但一个 warp 读 32 x 12 = 384 连续字节，访问仍然完全合并，
总事务数不变。

**别过度外推**：如果 kernel 的 SM 利用率本来就到 60~80%，float3 的额外指令
就会开始收税。float3 仍然是应该避免的写法，只是在这个 kernel 里它的代价被
隐藏了。

## EXP2 block size 扫描

| block | 耗时 | 带宽 |
|---|---|---|
| 64 | 4.218 ms | 179.0 GB/s |
| 128 | 4.228 ms | 178.6 GB/s |
| 256 | 4.228 ms | 178.6 GB/s |
| 512 | 4.227 ms | 178.6 GB/s |
| 1024 | 4.228 ms | 178.6 GB/s |

完全无差别。原因有两层：

- 这个 kernel 只用 18 个寄存器、0 字节共享内存，所以 64~1024 **每个配置的
  理论占用率都是 100%**。block size 影响性能的常见路径是"改变占用率"，
  这条路在这里根本不存在。
- Waves Per SM = 1170，尾部效应可以忽略。

## EXP3 并行度下限在哪（grid-stride, block=256）

| grid | warps | 耗时 | 带宽 |
|---|---|---|---|
| 14 | 112 | 4.255 ms | 177.4 GB/s |
| 28 | 224 | 4.272 ms | 176.7 GB/s |
| 112 | 896 | 4.312 ms | 175.1 GB/s |
| 896 | 7168 | 4.253 ms | 177.5 GB/s |
| 3584 | 28672 | 4.227 ms | 178.6 GB/s |
| 16384 | 131072 | 4.220 ms | 178.9 GB/s |

**grid = 14 就打满了** —— 每 SM 一个 block，总共 112 个 warp。整条曲线基本是
平的，从 14 涨到 16384 只差 0.8%。

所以"每个 SM 有充分的活干"这个条件比直觉上容易满足得多。真正需要的不是
"活多"，而是在途访存请求足够多（memory-level parallelism）。

用 Little's Law 估：维持 179 GB/s 吞吐、DRAM 延迟约 500~700 ns，
需要约 100 KB 数据同时在途。112 个 warp x 每次 float4 访存 512 字节 ≈ 57 KB，
再叠上编译器对循环的指令级流水就够了。

## 总结

三问指向同一个结论：

> vecadd 被 DRAM 独占，其余所有资源都有 90% 以上闲置。
> 在这种 kernel 里，指令数、向量宽度、block size、并行度组织全都不影响结果，
> 因为瓶颈资源早已饱和。

推论：**优化任何东西之前，先确认你要优化的那个资源不是已经闲置的。**
这就是阶段 0 要建立的核心判断力。

## 补充（2026-10-03）：并行度下限往下压，会看到什么

EXP3 只测到 grid=14（每 SM 一个 block），那时已经打满。这次用
`phase0/cuda/latency_probe.cu` **继续往下压**（grid = 1/2/4/7），
并对同一批数据加了 ILP 对照（每线程 4 笔独立请求）。
原始输出：`phase0/reports/latency_probe.txt`。

| grid | warps | 在途(ILP=1 估算) | ILP=1 带宽 | ILP=4 带宽 | 提升 |
|---|---|---|---|---|---|
| **1** | 8 | 4 KB | **36.9 GB/s** | 41.0 | +11 % |
| **2** | 16 | 8 KB | **71.0 GB/s** | 84.8 | +19 % |
| **4** | 32 | 16 KB | **128.9 GB/s** | 148.1 | +15 % |
| 7 | 56 | 28 KB | 180.7 GB/s | 185.4 | +2.6 % |
| 14 | 112 | 56 KB | 187.2 GB/s | 187.5 | 0 % |
| 28 | 224 | 112 KB | 187.6 GB/s | 187.7 | 0 % |

**断崖出现了：grid=1 只拿到 36.9 GB/s，是峰值（187）的 20 %。**

### 根因不是"在途字节总数不够"，而是"活跃 SM 数不够"

ncu 逐档实测（同一个 `read_gs` kernel）：

| grid | **DRAM 吞吐** | SM 吞吐 | 每 SM 占用率 | L1 吞吐 | 耗时 |
|---|---|---|---|---|---|
| 1 | **18.97 %** | 0.95 % | 24.99 % | 6.05 % | 6.92 ms |
| 2 | **36.72 %** | 1.84 % | 24.99 % | 11.77 % | 3.57 ms |
| 4 | **66.28 %** | 3.33 % | 24.97 % | 21.31 % | 1.98 ms |
| 14 | **97.57 %** | 4.97 % | 24.98 % | 31.78 % | 1.35 ms |

**每档的 DRAM 吞吐几乎与 grid 数成正比**：18.97 → 36.72 → 66.28。
也就是说 **一个 SM（一个 block）大约只能拉动 19 % 的 DRAM 带宽 ≈ 34 GB/s**：

```text
可用带宽 = min(DRAM 峰值, 每 SM 取数上限 x 活跃 SM 数)
         = min(187, 34 x grid)

  grid=1 -> 34   （实测 36.9）
  grid=2 -> 68   （实测 71.0）
  grid=4 -> 136  （实测 128.9）
  grid=7 -> 187  （实测 180.7，撞上 DRAM 峰值）
```

> **这才是"延迟导致资源空转"的真身**：grid=1 时 DRAM 只用了 19 %、
> SM 0.95 %、L1 6 % —— 所有资源都在闲着，因为**只有 1 个 SM 在向内存要数据**。

### ILP 能补，但只能补一点点

把每线程的在途请求从 1 笔加到 4 笔（在途量 ×4），只换来 **11 ~ 19 %** 的提升，
而且**突破不了每个 SM 的上限**（1 SM：37 → 41，离 187 还很远）。

> 结论：并行度不够时，**多加 block（更多 SM 参与）远比加 ILP 有效**。

### 两个必须记住的坑

1. **`sm__warps_active` 是"每个活跃 SM 的入住率"，不反映"有多少 SM 在活跃"。**
   上面四档它都是 ~25 %（8 warp / 32 warp），但 grid=1 时有 **13 个 SM 完全空闲**——
   这个指标一个字都没说。
2. **原始的"107 KB 在途量"估算偏保守**（`notes/03` §七 推的）。
   实测门槛低得多，而且真正的约束是"活跃 SM 数 x 每 SM 取数上限"。
