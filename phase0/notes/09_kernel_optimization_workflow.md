前置：`07_performance_factors.md`（因素表与五层漏斗）、`08_ncu_map.md`（怎么看指标）。
本文把它们串成一个**可执行的操作顺序**。

## 0. 先修正目标本身

### 0.1 官方 rules 和我们的表，各管什么（重要）

发现 `ncu --set full` 会直接输出带量化收益的建议（`Est. Speedup: xx%`）之后，
很容易产生"我们自己总结的方法没用了"的感觉。**准确的分工是这样：**

```text
第 1 层  ncu 官方 rules   ->  找症状 + 量化收益      （先跑 --set full）
第 2 层  本笔记的杠杆表   ->  解释成因 + 给候选手段
第 3 层  roofline / 屋顶  ->  还剩多少空间、什么时候停
```

第 1 层已经脚本化了，一条命令出清单：

```powershell
python phase0/ncu_rules.py phase0/cuda/sgemm.exe -k sgemm_reg2 --skip 3 `
    --out phase0/reports/sgemm_reg2_rules.md
```

输出示例（`sgemm_reg2` 的实测）：

| 类型 | 预计收益 | 官方结论 |
|---|---|---|
| OPT | 47.5 % | 调度器每 2.7 周期才发一条指令 |
| OPT | 44.8 % | 每个 warp 花 7.1 周期等 MIO 队列 |
| OPT | 31.6 % | 共享内存 store 有 1.5 路 bank conflict |
| OPT | 25.0 % | 理论占用率 75 %，受寄存器/共享内存限制 |
| OPT | 3.6 % | 共享内存访存未合并（524288 次额外 wavefront） |

| 问题 | 谁来回答 |
|---|---|
| 哪里有问题？ | **官方 rules**（它比人看得细，还能算出收益百分比） |
| **为什么会这样？** | 本笔记（rules 只说症状，不说因果链） |
| 先修哪一条？ | 本笔记（rules 会给 3 条互相重叠的建议，不说优先级） |
| 还剩多少空间、该不该停？ | roofline + 收敛判据 |
| **要不要换算法/换硬件？** | **只有人能回答** —— rules 只看你当前的实现 |

**我们的表被证明不够用的地方（2026-10-04 实锤）**：

| 官方查出来的 | 我们的表里有吗 |
|---|---|
| 全局 load 跨行（每线程只用 sector 的 7.1/32 字节） | 判据有（`sectors/请求`），但**没去测** |
| MIO 队列堵塞 48 % | **没有这一档** |
| 共享内存 bank conflict 31.5 % | **没有这一档** |

后两行已补进下面的杠杆表。

**"最低耗时"通常不是真实目标，而是"约束下的最优"：**

| 约束 | 说明 |
|---|---|
| 正确性 / 精度 | 破了约束的最快没有意义 |
| 可维护性 | 手写汇编快 3 % 但没人敢改，通常不值 |
| 开发时间 | 投入 3 天换 2 %，要问值不值 |
| 屋顶 | 物理上限。**"逼近屋顶"才是可达目标** |

还有一条更根本的：

> **有些 kernel 的最优解是"不要这个 kernel"** ——
> 把它融合进上游/下游，省掉一次完整的来回搬运。

## 1. 五步循环

```text
① 量基准（正确性 + 时间 + 配置）
        ↓
② 用 ncu 的 5 个数字判断"卡在哪一级"
        ↓
③ 按瓶颈类型查"杠杆表"，选 1~3 个候选手段
        ↓
④ 单变量实验：改一个 -> 量 -> 保留或回滚   <-- 循环
        ↓
⑤ 收敛判据满足 -> 停
```

### 第 0 步：量基准

没有基准就没有优化——你只是在改代码。

| 要做 | 为什么 |
|---|---|
| 正确性测试（对拍或解析解） | 优化后错了等于白做 |
| **独立运行**计时，N 次取平均 | 不能用 profiler 下的时间（笔记 08 坑 1） |
| 记下配置：数据量 / block / grid / 编译选项 | 否则结果不可复现 |
| 记 SM 频率 | 降频会让所有结论失真 |

产出：**一个可复现的毫秒数**。后面每次改动都跟它比。

### 第 1 步：判断卡在哪一级（先看四个吞吐，再钻一层）

> **先读官方结论，再用下表解释。** `ncu --set full` 输出的 INF / OPT / WRN 就是
> NVIDIA 内置的规则引擎给的判断，还带**量化的预计收益**（`Est. Speedup: xx%`）。
> 那才是权威入口；下面这些是我为了让你理解指标而整理的归纳，**属于二手解读**。

**先分清两类数字**（这是最容易混的地方）：

| 类别 | 指标 | 回答 |
|---|---|---|
| **吞吐 / 利用率** | `dram__throughput`、`lts__throughput`、`l1tex__throughput`、`sm__throughput` | **资源有多忙** |
| **占用率** | `sm__warps_active.avg.pct_of_peak_sustained_active` | **人手有多少** |

> 判断瓶颈看**吞吐**；占用率只用来解释"为什么吞吐上不去"。两者是不同维度，不能互相替代。

**第一步：比四个吞吐，谁最高谁是瓶颈。**

| 指标 | 它是什么 | 满了意味着 |
|---|---|---|
| `dram__throughput` | DRAM 带宽利用率 | 搬运量到顶 |
| `lts__throughput` | **L2** 的忙闲 | 缓存带宽到顶 |
| `l1tex__throughput` | **L1/TEX 单元**（含 LSU 取数、共享内存）的忙闲 | 取数/共享内存到顶 |
| `sm__throughput` | 官方 label 是 **Compute (SM) Throughput** | 见下方勘误 |

> **勘误（2026-10-04）**：本节早前写过"`sm__throughput` = SM 内最忙那条流水线"，
> **这个解释我没有官方依据，应视为不可靠**。实测反例：`sgemm_naive` 的
> `sm__throughput` 是 86.7 %，而官方流水线表（cycles 口径，见下）里最高的 FMA 只有 21.9 %——
> 两者对不上，说明它的构成比"取最大值"复杂。
> **判断流水线级瓶颈请用官方那张表，或直接读 ncu 的 rule 输出。**

**第二步：钻到流水线一级——用官方那张表，别自己拼指标。**

`ComputeWorkloadAnalysis` section 里有**两张**口径不同的表：

| 表 | 底层指标 | 含义 |
|---|---|---|
| **Pipe Utilization (% of active cycles)** | `sm__pipe_*_cycles_active...pct` | **流水线忙了多少周期**（把指令的执行周期数算进去）<- 判瓶颈用这张 |
| Pipe Utilization (% of peak instructions) | `sm__inst_executed_pipe_*...pct` | 指令条数占比（不管每条占几周期）<- 不是"忙的程度" |

实测（本机 sm_75）：

| kernel | `pipe_fma`（cycles） | `pipe_alu`（cycles） | `sm__throughput` |
|---|---|---|---|
| naive | **21.9 %** | 15.3 % | 86.7 % |
| tiled | 14.1 % | 3.6 % | 72.3 % |
| reg | **28.4 %** | 4.2 % | 27.4 % |

两个要点：

1. **官方口径下，三个版本的 FMA 流水线都不超过 29 %** —— 从来不是瓶颈。
   ncu 的 rule 也明说："FMA is the highest-utilized pipeline (27.6 %) ... **should not be a bottleneck**"。
2. **LSU 根本没有 cycles 计数器**（`sm__pipe_lsu_cycles_active` 在本机返回 `n/a`），
   所以官方的流水线表里不含它；`sm__inst_executed_pipe_lsu` 那个 87 % 是**指令条数口径**，
   只能说明"取数指令很多"，不能说明"LSU 忙到 87 %"。

**第三步：如果四个吞吐都低于 50 %，才轮到延迟。**

| 指标 | 结论 |
|---|---|
| `No Eligible`、stall 原因 | 资源不够 vs 延迟没藏住 |
| 有效带宽 vs 各级峰值 | 离屋顶还有多远 |

完整判断顺序：

```text
四个吞吐谁最高？
  |- dram  -> DRAM 档
  |- lts   -> L2 档
  |- l1tex -> 看 L1 命中率：低 = 访存模式档；高 = 取数密度档
  \- sm    -> 再钻 pipe：lsu 满 = 取数档；fma 满 = 算力档
没有明显最高者  -> 延迟档（看 No Eligible）
kernel 很短 -> 固定开销档
```

> 这是同一套顺序的速查版；详细判据与三个坑见下面「判别顺序」小节。

产出：一句话结论，必须是下面之一 ——
**卡在 DRAM / L2 / 延迟 / 指令发射 / 算力 / 固定开销**。
判断不出来就先别改代码。

#### 判别顺序：先找饱和的资源，再读症状

这些吞吐数字**不是并列的线索，是有先后的漏斗**。理由是：

> **症状是共享的，原因是互斥的。**
> "No Eligible 高"在延迟受限和带宽饱和时**都会**出现；
> 但"哪个资源被打满"在同一时刻只有一个答案。

所以顺序不能倒：

```text
① 四个吞吐（dram / lts / l1tex / sm）谁最高？
      有明显最高者 -> 就是它，别再拿 stall 去推翻它
            dram  -> 带宽受限      -> 减字节 / 提高复用
            lts   -> L2 带宽       -> 缩短复用距离
            l1tex -> 还要配 L1 命中率一起看：
                       命中率低 -> 访存模式档 -> 合并访问 / 改布局
                       命中率高 -> 取数密度档 -> 降低"取数:FMA"比
            sm    -> 钻到管道级（pipe_lsu / pipe_fma / ...）
                       pipe_lsu 最高 -> 取数密度档（同上）
                       pipe_fma 最高 -> 算力档 -> 减 FLOP
      没有明显最高者    -> 往下
② 资源都闲着，那就问"为什么没喂饱"
      占用率低                -> 住不满 -> LaunchStats 查是谁限制的
      占用率高 + No Eligible 高 -> 在等   -> 加在途请求（ILP/MLP、prefetch）
③ kernel 很短（和 13 us 启动开销同量级）-> 固定开销主导
```

**⚠️ 三个必须避开的坑（都是实测踩出来的）：**

| 坑 | 反例（本仓库实测） |
|---|---|
| **不要用固定阈值（如 80 %）** | `sgemm_tiled` 的 L1TEX 只有 **77.9 %**，但它就是瓶颈（同期 SM 65.7 %）。用 80 % 当门会漏判，然后掉进②得出"加在途请求"的错结论 |
| **`l1tex` 高不等于缓存档** | `sgemm_naive` L1TEX 88 %、**L1 命中率 94.9 %** -> 缓存没出问题，是取数指令太多。此处的"改布局"是错药（实测只换来 1.40x） |
| **`sm` 高不等于算力高** | `sm__throughput` 取的是各子单元最大值；naive 的 88 % 其实是 **LSU 87 %**，FMA 只有 22 % |

**① 必须在 ② 前面。** 一旦确认 DRAM 饱和，那个 `No Eligible 97 %` 就不再是
"延迟受限"的证据，而是"排队造成的延迟"——两者症状一模一样，**对策却相反**：
一个要加在途请求，另一个加多少都没用（下文 DRAM 档四次调参全部零收益）。

四个最容易翻车的混淆点：

| 混淆 | 两个可能 | 判别键 |
|---|---|---|
| `No Eligible` 高 | 延迟没藏住 / 带宽饱和排队 | **先看四个吞吐**（不只是 dram）；有资源饱和就是后者 |
| SM 利用率低 | 没活干 / 有活但在等 | 看 `warps_active`：低 = 没人，高 = 在等 |
| 占用率高 | 好事 / 无关 | 占用率**从来不是目标**：vecadd 占用率满、SM 只用 5 % |
| `sm__throughput` 高 | 算力受限 / 某条小流水线饱和 | 去 `ComputeWorkloadAnalysis` 看是哪条 pipe |

另有一条隐性坑：同一个指标 `_elapsed` 和 `_active` 两种后缀，在**占用率低**时
能差出好几倍（前者分母是整段 kernel 时长，后者只算 SM 上有 warp 的时间）。
跨报告对比前先确认后缀一致。

**最后一步永远是实验，不是指标。** 指标只给假设，验证靠"移除法"：
真瓶颈的话动它一定有效，非瓶颈的话怎么动都没用。

### 第 2 步：按瓶颈查杠杆表（核心）

| 卡在哪 | 典型特征 | **只能动这些** | **别浪费时间在** |
|---|---|---|---|
| **DRAM 带宽** | DRAM > 80 %，SM < 20 % | **减少搬运字节**：融合、降精度、不写无用输出；提高复用（tiling） | 向量宽度、block size、占用率、指令数 |
| **L2 带宽** | `lts__throughput` 最高 | **缩短复用距离**：分块、改循环顺序、改数据布局 | 只减总字节数（没用） |
| **访存模式**（L1 未命中太多） | `l1tex__throughput` 高 **且 L1 命中率低** | 合并访问、改布局（SoA/对齐）、缩短复用距离 | 降低取数:FMA（命中问题不是指令问题） |
| **取数密度**（访存指令太多） | `l1tex__throughput` 高 **但 L1 命中率高**，或 `pipe_lsu` 最高 | **降低"取数:FMA"比**（寄存器分块）、向量化 | 缓存优化（缓存没出问题） |
| **共享内存冲突** | 官方 rule 报 `bank conflict`；`l1tex__data_bank_conflicts_pipe_lsu_mem_shared.sum` | 加 padding（本仓库用 `+4`）、改 tile 排布、向量化取数 | 换 block size |
| **MIO 队列压力** | 官方 rule 报 `MIO throttle`；`smsp__average_warps_issue_stalled_mio_throttle...` | 减少共享内存/特殊功能指令、向量化取数 | 减少 FLOP |
| **访存模式效率低** | 官方 rule 报 "only X of 32 bytes utilized"；`sectors/请求` 高于理想值 | 合并访问、换索引映射、改布局 | 降低取数:FMA |
| **延迟** | 带宽和算力都不高，`No Eligible` 高 | **加在途请求**：提高并行度/占用率、ILP/MLP、prefetch、软件流水 | 减少字节数 |
| **算力（FMA）** | `sm__inst_executed_pipe_fma` 是全场最高的 pipe | 减少 FLOP、换更快的数据类型/指令 | 访存优化 |
| **固定开销主导** | 单次 kernel 很短（本机启动约 13 us，占比超 ~30 % 就该警惕）——**这是症状，不是目标** | **减少启动次数**：融合、CUDA Graph、持久化 kernel | 微优化 |

> 这张表的每一行都来自实测：本仓库里 DRAM 档的四次调参
> （向量宽度 / block size / 占用率 / 并行度）全部零收益，
> 就是因为瓶颈从头到尾都在 DRAM，杠杆表那一列全是空的。

#### 澄清 5：`l1tex__throughput` 高的两种成因——**看命中率区分**

这是最容易判错的一处。L1TEX 忙有两种完全不同的原因，修法相反：

| 成因 | 伴随特征 | 档 | 手段 |
|---|---|---|---|
| **未命中太多** | L1 命中率**低**（< 50 %）、`sectors/请求` 高于理想值 | **访存模式档** | 合并访问、改布局、缩短复用距离 |
| **指令太多** | L1 命中率**高**（> 80 %）、`pipe_lsu` 也高 | **取数密度档** | 降低"取数:FMA"比、向量化 |

**所以"L1TEX 高"不能直接判成缓存问题** —— 必须先看命中率。
实测例子（`reports/sgemm_qa.md`）：`sgemm_naive` 的 L1TEX 88 %，
但 **L1 命中率 94.9 %** —— 缓存完全接住了，忙的是**取数指令本身**。
这时"缩短复用距离/改布局"是**错的药**（`sgemm_tiled` 只快了 1.40x 就是这个原因）。

#### 澄清 6："L1 高 + SM 也高"不是两个瓶颈，是**同一个**

`sm__throughput` 的定义是"SM 内最忙那条流水线"。当最忙的是 **LSU（取数）** 时：

```text
LSU 每发一条访存指令 -> L1TEX 就要处理一次
所以：  pipe_lsu  88 %  ~=  l1tex__throughput  88 %  ~=  sm__throughput  88 %
        (谁在发)          (谁在处理)               (取最大值)
```

实测（sgemm_naive）：LSU 87.43 %、L1TEX 88.26 %、SM 88.23 % ——
**三个数字说的是同一件事**。看到它们一起高，别当成"两个瓶颈要同时解决"，
而是要意识到：**你看到的是同一条取数通路的三个视角。**

#### 澄清 1：那一列是"症状"，不是"目标"

"单次 kernel 很短"是**危险信号**，不是好事——它意味着固定开销占了很大比例：

```text
启动开销约 13 us
  30 us 的 kernel：13/30 = 43 % 的时间花在启动上
  60 us 的 kernel：22 %
 500 us 的 kernel：2.6 %   <- 这时才不用管
```

（实测：2048 次启动 = 28.0 ms，其中 26.8 ms 是启动开销，占 **96 %**。）

#### 澄清 2："延迟"分两层，手段完全不同

| 层 | 是什么 | 手段 | 在哪一侧 |
|---|---|---|---|
| **核内延迟** | 一个 kernel 内部，访存没回来导致的空转 | 提占用率、**加 ILP/MLP**（一个线程挂多笔独立访存）、prefetch、软件流水 | **设备侧**（改 kernel） |
| **核间 / 主机侧** | kernel 之间、主机与设备之间的空转 | **stream 并发**、异步拷贝、CUDA Graph、持久化 kernel | **主机侧**（改调度） |

- **grid / block 属于"核内"那一层**——它决定"能有多少 warp 同时在岗"。
  但它的有效性取决于**占用率是否受限**：本机实测 grid=14 就把带宽打满，
  加到 16384 只快 0.8 %（笔记 07 专题）。
- **stream 属于"主机侧"**——你的理解对：那是主机侧的调度策略，
  解决"不相干的活儿有没有并行起来"，不是"核内等料"。

#### 澄清 3：为什么"延迟没藏住"却"资源没空转"（vecadd 的实测悖论）

vecadd 的三个实测数字放在一起，看着是矛盾的：

| 指标 | 值 | 看起来说明 |
|---|---|---|
| `No Eligible` | **97.16 %** | 调度器 97 % 的周期找不到能干活的 warp |
| `Warp Cycles Per Issued Instruction` | 268 周期 | 平均等 268 拍才发一条指令 |
| `DRAM Throughput` | **93.31 %** | 带宽几乎打满 |

**调度器快闲死了，带宽怎么还能打满？**

因为 **DRAM 不需要"调度器一直发指令"来保持忙碌，它需要"有请求在排队"。**

```text
装卸口（DRAM）连续工作，是因为门口一直有货车排队。
哪怕车间班长（调度器）97 % 的时间发不出新指令，
已经排上队的那些货车照样在卸货。

要打满带宽：在途字节数 >= 带宽 x 延迟
           179 GB/s x ~600 ns  ≈  107 KB
```

vecadd 有 448 个常驻 warp，每个能挂若干笔读请求，
潜在在途量远大于 107 KB —— 所以**发射率只有 2.84 % 也够撑满 DRAM**。

> **结论：延迟没藏住（No Eligible 97 %），但资源没空转（DRAM 93 %）。
> 这种情况下"优化延迟"是零收益。**

**那"资源真的空转"长什么样？**（2026-10-03 补测，`latency_probe.cu`）

| grid | **DRAM 吞吐** | SM 吞吐 | L1 吞吐 | 实测带宽 |
|---|---|---|---|---|
| **1** | **18.97 %** | 0.95 % | 6.05 % | 36.9 GB/s |
| 2 | 36.72 % | 1.84 % | 11.77 % | 71.0 GB/s |
| 4 | 66.28 % | 3.33 % | 21.31 % | 128.9 GB/s |
| 14 | 97.57 % | 4.97 % | 31.78 % | 187.2 GB/s |

grid=1 时**所有资源都在 20 % 以下** —— 这才是"延迟让资源空转"。
而且根因不是"在途字节不够"，是**只有 1 个 SM 在要数据**：

```text
可用带宽 = min(DRAM 峰值, 每 SM 取数上限 x 活跃 SM 数)
         = min(187, 34 x grid)      <- 每 SM 约 34 GB/s（实测）
```

#### 澄清 4：怎么区分"真延迟瓶颈"和"假延迟瓶颈"

`No Eligible` 高是**症状**，不是**诊断**。它只说"调度器找不到活"，
而原因有两种，处理方式完全相反：

| 现象 | 含义 | 该做什么 |
|---|---|---|
| `No Eligible` 高 **+ 某个资源 > 80 %** | 那个资源满了，请求在排队 -> **延迟是结果，不是原因** | 去优化那个资源（vecadd 就是这种：去减少 DRAM 字节） |
| `No Eligible` 高 **+ 所有资源都 < 50 %** | 请求不够填满流水线 -> **延迟是真瓶颈** | 加并行度 / ILP / 向量化 |

**"在途字节数"的三个乘数**（实测显示第一个乘数最重要）：

```text
在途字节数 = 常驻 warp 数  x  每 warp 在途请求数  x  每请求字节数
                  |                    |                    |
             最多 block/SM           ILP / MLP            向量化
             （让更多 SM 参与）      多个独立访存错开       （float4 等）
                   ^                     ^
                最有效               只值 11~19 %
```

实测（`reports/membound_qa.md` 补充节）：把 ILP 从 1 提到 4（在途量 ×4），
只换来 11~19 % 的提升，**突破不了每个 SM 的上限**（1 个 SM：37 -> 41 GB/s）。
而多加 block（让更多 SM 参与）几乎线性增长：grid=1/2/4 -> 37/71/129 GB/s。

> **所以"延迟隐藏"的第一手段是"让更多 SM 有活干"，不是"让每个线程多挂几笔"。**

## 2. 手段清单（按性价比排序）

从"数量级收益"到"百分点收益"：

| 优先级 | 手段 | 典型收益 |
|---|---|---|
| 1 | 确认这个 kernel 能不能**消失**（融合进上下游） | 省掉整趟来回 |
| 2 | **减少搬运字节**（融合中间结果、降精度、不写无用输出） | 常见 1.5~2 倍 |
| 3 | **缩短复用距离**（tiling、改循环顺序） | 到 L2 后可达该级速率 |
| 4 | 提高并行度 / 在途请求数 | 没打满带宽时有效 |
| 5 | 减少指令（向量化、展开） | 指令受限时才有 |
| 6 | 微调（block size、占用率、缓存提示） | 通常几个百分点以内 |

**第 6 项放最后不是因为它没用，而是因为它最容易被误当成第一项。**
本仓库阶段 0 最大的收获就是证明了：瓶颈不在那一层时，第 6 项收益恒为零。

## 6. 本文引进的新名词（事后补登记）

| 名词 | 一句话 | 属于哪一类 |
|---|---|---|
| **CUDA Graph** | 把一串 kernel 启动"录"成一张图，之后**一次提交**执行整张图；把 N 次 CPU 侧启动开销压成 1 次 | 减少固定开销 |
| **持久化 kernel** | 启动一个常驻 kernel（block 数 = 全机容量），循环领任务、**永不退出**；一次启动处理所有活 | 减少固定开销 |
| **软件流水** | 把"读下一块"和"算当前块"错开，让访存延迟被计算盖住 | 延迟隐藏（核内） |
| **ILP / MLP** | 指令级 / 内存级并行：一个线程同时挂多笔**独立**的访存 | 延迟隐藏（核内） |
