# 笔记 07 · GPU 性能因素总表

## 主题

- 本次主题：**写 CUDA 代码时要考虑哪些因素才能更快**，以及每个因素**什么时候不用管**
- 来源资料：本仓库的实测产出（`hardware.json`、`reports/*`、`notes/01–06`）+
  官方 CUDA C++ Programming Guide ch.5（性能指南）与 Best Practices Guide
- 对应清单：`LEARNING_PATH.md` 的 C 组（性能工程）为主，B/C/D 组均有覆盖

---

## 一句话总览

> **性能不是"调出来的"，是"判断出来"的。**
> 先确定卡在哪一级资源，再动对应那一级唯一有效的旋钮；
> 其余所有旋钮在当前场景下都是零收益——这一点比旋钮本身重要。

---

## 结构框架：五层漏斗（决策顺序）

```text
0. 测量      不测不优化：先看这个 kernel 卡在哪一级
      ↓
1. 屋顶      数据量 / 工作集决定屋顶是哪一条：L1 → L2 → DRAM
      ↓
2. 搬运      [DRAM 档] 每元素搬几字节？还能更少吗？（融合 / 降精度 / 不写无用输出）
      ↓
3. 并行      在途请求够不够喂满这一级？（并行度 / 占用率 / 延迟隐藏）
      ↓
4. 指令      SM 侧是不是瓶颈？（指令混合 / 发射率 / 寄存器）
      ↓
5. 规范      这条结论可复现吗？（计时方法 / 原始证据）
```

**顺序不能颠倒**：第 2 步没做完就去调第 3、4 步，就是本仓库已经证伪过的那些尝试。

## 常见混淆点

| 容易混淆 | 事实 | 出处 |
|---|---|---|
| 指令数少 = 快 | `float3` 访存指令是 `float4` 的 3 倍，性能一样——瓶颈在 DRAM 时指令免费 | 笔记 06 §4 |
| SM 利用率低 = SM 闲着 | 可能是**卡住了在等料**（No Eligible 97 %），不是"算得快所以闲" | 笔记 01 §0 |
| 占用率越高越好 | 够用即可；18 寄存器时 64–1024 的 block 全 100 %，性能完全一样 | 笔记 03 §六 |
| L2 命中率 = 数据复用率 | 33 % 全部来自**写**（写满 sector 不需要取数），读命中只有 0.03 % | 笔记 05 §7、06 §3 |
| 峰值是能达到的目标 | 实测只有理论值的 93 %，这就是健康状态 | 笔记 03 §十三 |
| 把 `c=a+b` 改成 `a+=b` 能省流量 | 省不了：读 a + 读 b + 写 a 同样是 12 B/元素 | 笔记 07 本轮讨论 |

## 专题：数据量固定时，block size 和并行度、总时间是什么关系

### 一句话

> **总搬运时间 = 搬运字节数 ÷ 有效带宽。**
> 数据量固定时，分子就是常数，所以 block size 想影响时间**只有一条路：改变有效带宽**。
> 而它改变带宽的途径只有三条——占用率、尾部效率、合并访存。vecadd 把这三条全堵死了，
> 所以怎么调都一样。

### 第 1 步：先纠正一个术语混淆

block size 不是并行度。三个层次要分开：

| 叫法 | 定义 | 由谁决定 | block size 能改吗 |
|---|---|---|---|
| **名义并行度** | 总线程数 / 总 warp 数 | **数据量** ÷ 每线程元素数 | **不能** |
| **实际并行度** | 同时驻留在 SM 上的 warp 数 | 占用率 × 32 warp/SM × 14 SM | 仅在影响占用率时能 |
| **有效并行度** | 同一瞬间在途的访存请求数（MLP） | 上面两条 + 每 warp 挂几笔请求 | 间接 |

核心事实：

```text
总线程数   = N / 每线程元素数        <- 与 block size 无关
总 warp 数 = 总线程数 / 32           <- 与 block size 无关
block 数   = ceil(N / block)         <- 与 block size 有关，但不改变总工作量
```

vecadd 的 N = 64 Mi、每线程 1 个元素 → **2,097,152 个 warp**。
block 从 64 调到 1024，这个数**一个都不变**，变的只是"把它们分成几堆"。

### 第 2 步：block size 影响时间的三个通道，及其本机情况

| 通道 | 机制 | 本机 vecadd |
|---|---|---|
| **占用率** | 寄存器×block、共享内存×block、每 SM 最大 block 数（Turing = 32）、每 SM 1024 线程上限 | 18 寄存器 + 0 共享内存 → 64~1024 **全是 100 %**，**此路不通** |
| **尾部效应** | `block 数 = ceil(N/block)`，最后一波没填满就浪费 | Waves Per SM = **1170**，尾部 < 0.1 %，**此路不通** |
| **合并访存** | warp 内地址的连续性由线程编号方式决定，与 block 多大**无关** | 已满分（sector 数 = 字节数/32），**此路不通** |

三条路全堵死 → 实测就是一条平线：

| block | 耗时 | 带宽 |
|---|---|---|
| 64 | 4.218 ms | 179.0 GB/s |
| 128 | 4.228 ms | 178.6 GB/s |
| 256 | 4.228 ms | 178.6 GB/s |
| 512 | 4.227 ms | 178.6 GB/s |
| 1024 | 4.228 ms | 178.6 GB/s |

极差 **0.24 %**，在噪声里。（`reports/membound_sweep.txt` EXP2）

### 第 3 步：那"并行度"到底要多少才够

EXP3 用 grid-stride 固定 block=256、只调 grid：

| grid | warps | 耗时 | 带宽 |
|---|---|---|---|
| **14** | 112 | 4.255 ms | 177.4 GB/s |
| 28 | 224 | 4.272 ms | 176.7 GB/s |
| 896 | 7168 | 4.253 ms | 177.5 GB/s |
| 3584 | 28672 | 4.227 ms | 178.6 GB/s |
| 16384 | 131072 | 4.220 ms | 178.9 GB/s |

**grid = 14 就打满了**（每个 SM 一个 block，共 112 个 warp），从 14 加到 16384 只快 **0.8 %**。

所以并行度不是"越多越快"，而是"**够喂满装卸口就行**"。这也是上面那条
"名义并行度由数据量决定"的意义：数据量大，你**不得不**派很多 warp；
但需要同时在岗的只有那么几十个。

### 第 4 步：什么时候 block size 真的会改变时间

| 场景 | 为什么变了 | 该往哪调 |
|---|---|---|
| 每线程寄存器多（> 64） | 大 block 的寄存器需求会撞上分配粒度 | 减小 block，或降寄存器用量 |
| 用共享内存 | 每 block 的共享内存 × 驻留 block 数 撑爆 64 KB | 按 tile 需求反定 block |
| **N 很小**（wave 数 < 10） | 尾部浪费占比大，一波只填一半就是 50 % 损失 | 让 grid 正好是 SM 的整数倍，或 grid-stride 固定 grid=14 |
| 需要 `__syncthreads` | 同步开销随 block 内 warp 数上升 | 减小 block |
| block 太小（如 32 线程） | 撞上"每 SM 最多 32 个 block"的上限 | 至少 64~128 |

> 注意：这几条的**机制**有官方依据（占用率公式、硬件上限），但**在本机还没实测过**
> （本机的 vecadd 属于"三条路全堵死"的极端干净样本）。所以它们是**待验证**，
> 不是已验证结论——列在下一节的待验证问题里。

### 补：block size 通过"占用率 -> 复用距离"间接影响命中率

推理链（用来回答"block 改成 1024，复用距离会变吗"）：

```text
block size  ->  占用率（每 SM 驻留线程数）  ->  复用距离  ->  L2 命中率
```

关键事实：**常驻线程数由硬件上限决定，与 block size 无关。**

```text
常驻线程数 = 14 SM x 1024 线程/SM = 14,336      <- 硬件上限，不是 block 决定的
每轮全芯片搬入 = 14,336 x 8 B = 112 KB          <- 所以复用距离与 block size 无关
```

于是：

| block size | 每 SM 常驻 block | 常驻线程 | 占用率 | 复用距离 | 命中率 |
|---|---|---|---|---|---|
| 256 | 4 | 1024 | 100 % | 112 KB | 不变 |
| 1024 | 1 | 1024 | 100 % | 112 KB | 不变 |
| 512 / 128 / 64 / 32 | 2 / 8 / 16 / 32 | 1024 | 100 % | 112 KB | 不变 |
| 768 | 1 | **768** | **74.57 %**（实测） | **84 KB** | **不变**（实测） |
| 192 | 5 | **960** | **93.20 %**（实测） | 105 KB | 不变（实测） |

**实测结果（2026-10-03，`cache_probe.exe bs`）**：

| block | 占用率 | L2 命中 | 耗时 |
|---|---|---|---|
| 256 | 99.61 % | 99.23 % | 0.929 ms |
| 1024 | 99.60 % | 99.21 % | 0.913 ms |
| 192 | 93.20 % | 99.22 % | 0.947 ms |
| 768 | **74.57 %** | **99.22 %** | 0.929 ms |

**占用率预测对了（768 -> 74.57 %，推算值 75 %），但命中率纹丝不动** ——
因为命中率已经**贴着理论上限**：

```text
每线程访问 = 128 轮 x 2 读 + 1 写 = 257
义务未中   = 2（a[i]、b[i] 首次读）
理论最高   = (257-2)/257 = 99.22 %   <- 实测 99.21~99.23 %，已饱和
```

> **修正后的规则：block size（-> 占用率）影响命中率，只在"复用距离接近缓存容量"时才有意义。**
> 这里复用距离（84~112 KB）离 1 MB 差 10 倍，命中率没有可提升空间。
> 想看到这个效应，得把工作集调到"刚好装不下"的临界点（复用距离 ~0.5~2 MB）。

顺带一个发现：block=768 占用率只有 74.57 %，耗时却只比满占用率慢 **1.7 %** —— 
又一次印证"**占用率够用就行，高了不等于快**"（因素 #6）。

**2026-10-03 补充：临界点实验做完了，规则被证实。**

用 `cache_probe.exe k`（每个线程处理 k 个元素 -> 复用距离 = 常驻线程数 x k x 8 B）：

| 条件 | L2 命中 | 结论 |
|---|---|---|
| 复用距离 224 KB / 672 KB / 896 KB（远离 1 MB） | 97.4 ~ 98.4 % | **占用率 99 % vs 75 % 没差别** |
| 复用距离 1008 KB（刚好压线） | 71.28 % | 有效容量略低于标称 1 MB |
| 复用距离 1344 KB | **0.85 %（256）/ 71.28 %（768）** | **占用率把它拉开 84 倍** |
| 复用距离 1792 KB | 0.49 % | 几乎全 miss，DRAM 吞吐冲到 93 % |

> **完整表述：占用率（以及所有缩短复用距离的手段）只在"复用距离接近缓存容量"时
> 才影响命中率。远离容量时，它一点用都没有；跨过容量时，它是断崖式的影响。**

另外，"命中率高"不等于"更快"——降低占用率是拿**延迟隐藏能力**换**更短的复用距离**：

```text
k=12：768（75 % 占用）比 256 快 6 %   <- 省下的 DRAM 流量更值钱
k=16：768 反而慢 14 %                <- 命中率只剩 32 %，DRAM 仍是瓶颈，却少了人手
```

## 掌握度检查（请先自己答，再对照）

按掌握度标准，"能解释 + 能应用 + 能迁移"才算掌握。下面三题分别验**复述、改错、迁移**：

**Q1（复述）** 一个陌生 kernel 的 ncu 报告显示：`DRAM Throughput 91 %`、
`Compute (SM) Throughput 8 %`、`sectors/请求 = 24`、每线程访问 16 字节。
先动哪个因素？为什么？

**Q2（改错）** 有人说："把 `float4` 换成 `float2`，每次搬的字节少了，带宽就省下来了。"
这句话错在哪？请用 sector 数说明。

**Q3（迁移）** 如果数组只有 64 KB，反复做 `c = a + b` 一万次，
本笔记里的哪些结论**不再适用**？为什么？

**Q4（复述 + 变式）** 数据量固定为 N。把 block 从 256 改成 512，请分别说出
**总 warp 数**、**block 数**、**有效带宽** 会不会变；如果会变，是在什么条件下变？

> 答案与评分见下一轮；没答上来不算问题，说明对应那一环需要补，回到表里第几行即可。

### Q1 评分（2026-10-03）

**答对的部分**：`DRAM 91 %` 判成带宽受限，并提出"少搬运 / 提高 AI"——
杠杆方向完全正确（对应流畅度：能判断瓶颈类型）。

**漏掉的部分**：`sectors/请求 = 24` 配上每线程 16 字节，等于**1.5 倍浪费**。
这才是"先动哪个"的答案——修访存模式（24 → 16）能直接砍掉 **1/3 的 DRAM 流量**，
而且不用改算法，比融合 / 降精度更便宜。原来那两个手段要等这一步做完才排得上。

**判定：Level 2（会用）** —— 能套 roofline 判断瓶颈类型，但还没把第二个信号
（sector 效率）纳入决策。按掌握标准，只到"会用"不算掌握。

**补强题（Q1b）**：某 kernel 每线程读 16 B，实测 `sectors/请求 = 24`。
把访存步长修正到 16 B 之后，理想情况下耗时能降多少？
（提示：时间 = 搬运字节数 ÷ 带宽，带宽不变）

### Q5 评分（2026-10-03）：步长题

题目：warp 里 32 个线程各读 `a[i*8]`（间隔 32 B），求 sectors/请求、每 sector 用到几个
float32、浪费多少。

**三项全对**：`sectors/请求 = 32` ✓ · 每 sector 只用 **1 个** float32 ✓ · 浪费 **7/8** ✓

补充一个同义说法：**浪费 7/8 = 多搬 8 倍**（理想 4 个 sector，实际 32 个，
`32 / 4 = 8`）。"7/8"说的是没被用到的比例，"8 倍"说的是开销倍数——
两个数都对，看你想强调哪一面。

**判定：Level 3（会改）** —— 能对一个没见过的访问模式独立算出 sector 代价，
并识别出"步长"这个根因。距 Level 4（会设计）还差一步：**主动选择布局**，
比如"这个 kernel 我打算用 SoA，因为……"。这正好是 C9（共享内存与 tiling）要练的。

### Q1b 评分（2026-10-03）：24 → 16 能省多少

答：**省 1/3 的搬运时间** ✓

推导（两种等价说法，别混）：

```text
DRAM 流量：24 -> 16 个 sector，降到 16/24 = 2/3
耗时      ：字节数 / 带宽，带宽不变 -> 降到 2/3

所以：耗时 -33%      <- "省 1/3"
      速度 x1.5      <- "快 1.5 倍"
```

**"省 1/3"和"快 1.5 倍"是同一件事**。容易搞混的地方：耗时降 33 % ≠ 速度升 33 %。
口头描述优化收益时，统一说"耗时降到原来的一半/三分之二"最不容易出错。

**判定：Level 3（会改）** ✓

### Q2 评分（2026-10-03）：float4 换 float2 省带宽吗

答：总数不变、每次少搬、对齐且 sector 用满、请求次数变多、实测没变化 —— **推理链正确** ✓

精确化的说法（把"感觉"变成"不变量"）：

> **决定 DRAM 账本的是总字节数，而不是每次请求搬多少。**
> 总搬运量只由"要处理多少数据"决定：`float4` 时是 N/4 个线程 × 16 B，
> `float2` 时是 N/2 个线程 × 8 B，**总字节数完全相同**。

本机证据（同一台机器、同样 512 MiB 数据、只改向量宽度）：

| kernel | 每线程 | sectors/请求 | **L1 ld sector 总数** |
|---|---|---|---|
| `vecadd_naive`（float） | 4 B | 4 | **16,777,216** |
| `vecadd_float4` | 16 B | 16 | **16,777,216** |

**每请求 sector 数差了 4 倍，总数一个不差。** 这就是"换向量宽度省不了带宽"的直接证明。

你补的那句"请求次数变多"也对：同样 512 MiB，`float2` 的请求数是 `float4` 的 2 倍。
它影响的是**指令数**和 **L1 请求流水线**，不影响 DRAM 账本——所以在带宽受限时免费。

**但这条结论有前提**（这是 Level 3 到 Level 4 的分界）：

| 条件 | 换向量宽度有没有收益 |
|---|---|
| 瓶颈在 DRAM（本机 vecadd：DRAM 93 % / SM 5 %） | **没有**，请求多出来的开销被闲置资源吸收 |
| 瓶颈在指令或 L1 请求（SM 利用率高了） | **有**，请求次数会开始收税 |

所以正确表述是："**在带宽受限的前提下**，向量宽度不影响总时间和总流量"，
而不是"向量宽度永远不重要"。

**判定：Level 3（会改）** —— 能独立完成这条推理；补强点是**主动说出适用条件**，
而不是靠"实测感觉没变化"来下结论。

### Q3 评分（2026-10-03）：64 KB 反复跑一万次

答：搬运减少到万分之一、AI 增加很多、性能提升很大。**前两句对，第三句错。**

**对的部分**

- DRAM 搬运确实降到约 1/10000：192 KB（首次）对比 1.92 GB（每次都走 DRAM）
- AI 确实暴涨：按 DRAM 口径从 0.083 涨到约 833，**跨过转折点 15.4**

**错的部分**：性能未必提升，反而可能更慢。三个原因：

**1. 总搬运量没减少，只是换了账本**

| 账本 | 大数组（768 MiB） | 64 KB x 10000 次 |
|---|---|---|
| DRAM 口径 | 805 MB | **192 KB**（只有第一次） |
| L2 / 片上口径 | 805 MB | **1.92 GB**（每次迭代重读） |

所以"AI 增加"的真相是**分母换了**，不是活儿变少了。

**2. 瓶颈换了屋顶**：DRAM 不再是限制，但 L2 带宽和算力成了新的上限。
这正是笔记 05 盲区 2 说的"需不需要分层 roofline"。

**3. 数据量太小 → 并行度和启动开销主导**（最关键的一条）

```text
64 KB = 16K 个 float  ->  512 个 warp（1 线程 1 元素）
机器常驻容量：14 SM x 32 warp = 448 个 warp
512 / 448 = 1.14 个 wave  ->  第二波只填满 14 %，尾部浪费约一半

理想搬运时间：192 KB / 179 GB/s      ~ 1.1 us
一次 kernel 启动开销                   3 ~ 5 us   <- 比搬运本身还长
```

> **勘误（2026-10-03）**：这里最初写的是"14 个 SM 里只有一个能分到活"，**是错的**。
> 那个说法只在"用一个 block 干完全部"（`<<<1, 1024>>>`）时成立。按朴素的
> 1 线程 1 元素写法（grid = 64 个 256 线程的 block），14 个 SM 都会参与，
> 真正的问题是**只有 1.14 个 wave**，第二波几乎空转。

两种"反复一万次"的写法，结论差 20 倍：

| 写法 | 启动次数 | 估算耗时 |
|---|---|---|
| CPU 循环启动 10000 次 kernel | 10000 | 10000 x 4 us ~ **40 ms**（启动开销占 95 %） |
| 一个 kernel 内循环 10000 次 | 1 | 约等于 L2 往返，量级 ms |

对比原来的 768 MiB 版本（4.5 ms）——**小数据量并没有更快，反而更慢**。

**这题要记住的**：

> **数据量变小 ≠ 变快。** 数据量小到一定程度后，瓶颈从"带宽"变成
> "并行度不足 + 启动开销"，roofline 的稳态假设失效——它的前提是"长期稳定地搬数据"。

**失效清单**

| 结论 | 还适用吗 | 原因 |
|---|---|---|
| 数据量决定屋顶是哪条 | 适用 | 但屋顶从 DRAM 换成了 L2 |
| 每元素 12 B / AI = 0.083 | **失效** | DRAM 口径不再代表真实流量 |
| DRAM 93 % 是瓶颈 | **失效** | DRAM 只在第一次被用到 |
| 14 个 block 就打满 | **失效** | 数据量根本派不出这么多 block |
| 93 % 效率算健康 | **失效** | 不是稳态，启动开销主导 |
| 合并访存 / sector 记账 | 仍适用 | L1/L2 依然按 sector 记账 |
| 计时必须刷 L2 | **更适用** | 不刷测的就是 L2 速度冒充 DRAM 速度 |

**判定：Level 2（会用）** —— "搬运减少 → AI 增加"这条链推得对，
但漏掉了"瓶颈转移"和"小数据量的代价"。

**补强题（Q3b）**：把场景改成 **64 MB**（仍然远大于 1 MB 的 L2），其他不变。
这时上面哪些结论会重新适用？为什么？

### 追问：为什么不干脆把 64 KB 放进共享内存 / 寄存器，原地循环一万次？

**方向是对的**——这正是片上复用（tiling / persistent kernel）的思路，阶段 1 的矩阵乘法就靠它。
但有三道墙挡着：

**1. 容量墙**

| 存储 | 本机容量 | 装得下 3 x 64 KB = 192 KB 吗 |
|---|---|---|
| 共享内存 / SM | 64 KB（每 block 默认 48 KB，opt-in 最多 64 KB） | 装不下 |
| 寄存器 / SM | 65536 格 x 4 B = **256 KB** | 总量够，但要 1024 线程 x 48 格/线程 |
| L2 | 1 MB | **装得下** <- 所以数据其实已经在 L2 里了 |

**2. 位置墙（这才是要害）**

**共享内存和寄存器都是"每个 SM 私有"的。** 把 192 KB 塞进一个 SM，
就意味着**只有那一个 SM 在干活**，另外 13 个闲置——算力和带宽都只剩 1/14。
换句话说：**片上存储能救"搬运"，救不了"并行度"。**

**3. 正确做法：分块，而不是整体塞进去**

```text
把 64 KB 的活切成 14 块（或更多）
每块 ~4.6 KB x 3 个数组 = 14 KB   ->  装得进共享内存
每块交给一个 SM / block，块内循环一万次，中间结果留在片上

结果：14 个 SM 全用上 + DRAM 流量降到 192 KB（一次读 + 一次写）
```

这就是 **persistent kernel + tiling** 的雏形。

**4. 写回问题：中间结果不用回 GM**

- 如果下游不需要中间结果（只要最终值），那 9999 次中间结果**完全不必写回**，
  这正是**融合**的价值：两个 kernel 合成一个，中间量留在片上。
- 最终结果还是要写回一次（除非只输出一个标量）。
- 而且 64 KB 的结果会被 **L2 接住**（1 MB 的 L2 装得下），如果下一个 kernel 紧接着用，
  可能连 DRAM 都不用到——这是 L2 存在的另一个理由（笔记 06 §3）。

### L2 是自动的，但"装得下"≠"一定命中"

**谁决定放什么**（接笔记 03 的比喻）：

| 存储 | 谁决定 | 你能控制什么 |
|---|---|---|
| 寄存器 | 编译器 | 代码结构影响用量 |
| 共享内存 | **程序员** | 显式分配、显式搬运 |
| L1 | 硬件 | 只有提示（`.cg` / `.cs`） |
| **L2** | **硬件，全自动** | 只有提示 + **访问顺序** |
| DRAM | 硬件 | 访问模式 |

L2 的填充、淘汰、替换**全部由硬件决定**，没有任何直接控制
（sm_80+ 有驻留控制，本机没有——笔记 06 §4 实测过 `discard` 被 ptxas 拒绝）。

**"装得下"只是必要条件**，三个条件同时满足才有命中：

| # | 条件 | 不满足会怎样 |
|---|---|---|
| 1 | 容量：工作集 <= 1 MB | 数据进来就被挤出去 |
| 2 | **复用距离**：两次用同一块数据之间搬过的字节数 <= 1 MB | 第二次要用时它早被淘汰了 |
| 3 | 无冲突：各数组地址没撞在同一个 set 上 | 容量够也会互相挤（冲突缺失） |

**条件 2 是关键，也是 tiling 的全部理论基础**：

```text
"总工作集装得下吗"  <- 这是错的问题
"两次用同一块数据之间隔了多少别的数据？"  <- 复用距离，这才是对的
```

| 场景 | 总工作集 | **复用距离** | L2 命中 | 状态 |
|---|---|---|---|---|
| vecadd（768 MiB，零复用） | 805 MB | — | **0.03 %** | 实测 |
| 64 KB，按元素循环 2048 轮 | 192 KB | 约 0 | **99.93 %** | 实测 |
| 256 KB，按元素循环 512 轮 | 768 KB | 约 0 | **99.80 %** | 实测 |
| 1 MB，按元素循环 128 轮 | 3 MB | 约 0 | **99.23 %** | 实测 |
| 64 MB，按元素循环 2 轮 | 192 MB | 约 0 | **59.99 %** | 实测 |
| 64 MB，**按数组遍历**（不分块） | 192 MB | 192 MB | 接近 0 | 未实测 |

> **勘误（2026-10-03）**：这里原本预测"64 MB 反复跑 -> 复用距离 192 MB -> 全不中"，
> **实测是 59.99 % 命中，DRAM 流量只有义务流量**。错因是没区分**循环结构**：
> 按数组遍历（读 a 全部 -> 读 b 全部 -> …）的复用距离才是 192 MB；
> 而"每个线程守着自己的元素反复读"的复用距离约等于 0。
> **同样的数据量，循环结构一变，命中率从 ~0 % 变成 ~100 %。**

最后两行就是 **Q3b 的答案**：64 MB 装不进 1 MB，
但如果把循环结构改成"每块内部反复用"的形式，复用距离就被压到 1 MB 以内，L2 照样有效。
完整实测见 `reports/cache_reuse_qa.md`。

```text
不分块：读 a[0..64MB] -> 读 b[0..64MB] -> 写 c[0..64MB] -> 下一轮重来
        两轮之间隔了 192 MB  >>  1 MB        -> 全 miss

分块：  把 64 MB 切成 64 块（每块 1 MB 的量），块内循环一万次
        块内两次访问之间只隔几 KB            -> 几乎全中
```

> **分块（tiling）不是"把整个工作集塞进缓存"，而是"安排访问顺序，
> 让复用距离小于缓存容量"。** 这是阶段 1 矩阵乘法的全部秘密。
