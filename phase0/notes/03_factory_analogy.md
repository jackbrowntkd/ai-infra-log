# 概念笔记 03 · 用一个工厂把 GPU 讲明白（v2 修订版）

术语太多记不住，这一篇只用一个比喻：**GPU 是个工厂**。
所有数字来自本机实测（`phase0/reports/device_query.txt`）。

> **v2 修订说明**：初版里我把「工人」同时用来指「线程」和「FP32 运算单元」，
> 导致「32 人的班组只有 16 个工人」这种矛盾。这一版把两者分开命名，
> 而且这个区分本身就是硬件上真实存在的（见第一节）。
> 同时补上了每个术语的英文原名。

---

## 一、先分清两种"人"：工人 vs 工作台

这是最容易糊的地方，也是初版出错的地方。

| 概念 | 比喻 | 是真实的吗 | 数量 |
|---|---|---|---|
| thread（线程） | **工人** | 虚拟的，只是一张任务单 | 你启动多少个就有多少个 |
| FP32 lane（运算通道） | **工作台** | **真实的硬件** | 每个工位组 16 个 |
| register（寄存器） | 工人专属的**储物格** | 真实 | 每个工人有自己的格子，格子放在车间的公共柜子里 |

- **thread（线程）**：工厂里并没有几百个真实的"工人"。线程是**逻辑上的工人**，
  本质是"一份任务 + 一套私有数据"。
- **FP32 lane**：工作台才是**真实的硬件**。工位组里只有 16 个。

**关键推论**：一个班组有 **32 个工人**，但工位组只有 **16 个工作台**。
所以同一条口令要**分两批**执行（每批 16 人上台）。

### 寄存器到底是"每线程"还是"每工作台"

**答案：每线程（per thread），不是每工作台。**

这一条特别容易绕晕，把两件事分清楚就通了：

- **工作台（lane）= 执行的位置**，只有 16 个。任何时刻台上站着谁，谁就在执行。
- **寄存器 = 存储的位置**，是一个**大池子**，本机每个车间有 65536 个格子。

寄存器池是**按工人（线程）分配**的，不是按工作台焊死的：

```
每个线程分到 R 个寄存器（vecadd 是 18 个）
一个班组 32 个工人 -> 占 32 x R = 576 个格子
```

**直接证据**：ncu 里那个指标的名字就叫 `Registers Per Thread = 18`，
明摆着是按线程算的。

**为什么必须这样设计？** 因为班组长等料的时候，他手上的数据不能丢。
一个车间同时住着 32 个班组 = 1024 个工人，每个工人的状态都得存着，
所以需要 1024 x R 个格子。

> 工作台只有 16 个，格子却要成百上千个 ——
> **执行的位置和存储的位置根本不是一回事，数量也不该一样。**

**这也正好解释了"为什么寄存器用量会限制占用率"**：
格子池只有 65536 个，每个工人占得越多，能住进来的工人就越少。

| 每线程寄存器 | 车间最多住多少工人 | 折合班组 | 占用率 |
|---|---|---|---|
| 18 | 3640（被 1024 上限卡住） | 32 | 100 % |
| 64 | 1024 | 32 | 100 % |
| 128 | 512 | 16 | 50 % |
### 一个格子有多宽

**一格 = 32 位。**

| 类型 | 宽度 | 占几格 |
|---|---|---|
| half（fp16） | 16 位 | 挤一挤，两个塞一格 |
| float32 / int32 | 32 位 | **正好 1 格** |
| double / int64 / 指针 | 64 位 | **2 格** |

> 每车间的柜子总容量 = 65536 格 x 32 位 = **256 KB**，
> 比共享内存（64 KB）还大 4 倍。

**验证方法**（代码 `phase0/cuda/reg_width.cu`，两条独立证据互相印证）：

证据 1 —— 直接看 PTX。`mov.b64 {%0,%1}, %2` 这条指令的字面意思就是
"把一个 64 位值拆进两个 32 位寄存器"：

```
原始 64 位值 : 0x1122334455667788
  hi = 0x11223344
  lo = 0x55667788
```

证据 2 —— 同样让每个线程"养着 8 个值"，看 ptxas 报的用量：

| kernel | 寄存器数 |
|---|---|
| `pairwise<8, float>` | 15 |
| `pairwise<8, double>` | 24 |

差 9 格，正好对应"8 个 double 比 8 个 float 多占一倍"。

> 这个实验失败了两次才做对，值得记下来：
> 第一次 kernel 太小，寄存器全被地址计算吃掉；
> 第二次编译器**推迟加载**来压低寄存器压力，写循环根本逼不出"同时活着"。
> 最后改用"两两相乘"才逼住。
> **教训：测寄存器用量时，要小心编译器会主动帮你省寄存器。**

**这个知识直接解释了 vecadd 为什么用 12 / 18 个寄存器：**

| 东西 | `naive` 占几格 | `float4` 占几格 |
|---|---|---|
| 索引 i | 1 | 1 |
| 指针 a / b / c | 2 x 3 = 6 | 2 x 3 = 6 |
| 字节步长常量（4 / 16） | 1 | 1 |
| 读回来的数据 | 1 + 1 | 4 + 4 |
| 结果 | 1 | 0（原地覆盖输入） |
| 记账（栈指针等） | 2 | 1 |
| **合计** | **12** | **18** |

> `int n` **不占寄存器**：它是 kernel 参数，住在常量区 `c[0x0][0x178]`，
> 用的时候直接读，不需要常驻。
> 上表和真机 `ptxas -v` 报的 12 / 18 **完全对上**（推导过程见本章最后一节）。

**注意一个指针就占两格** —— 传很多指针的 kernel，光地址就吃掉不少预算。

**实用推论**：

- 能用 float 就别用 double（除非精度真的需要），double 会让寄存器用量翻倍，
  占用率可能直接腰斩
- 算 fp16 时用 `half2` 打包，两个值挤一格，效率翻倍
### 统一规则：占几格 = 向上取整(宽度 / 32)

指针和 float4 看着是两种东西，其实遵守**同一条规则**：

| 类型 | 宽度 | 占几格 |
|---|---|---|
| half（fp16） | 16 位 | 半个，两个挤一格 |
| float / int32 | 32 位 | 1 |
| float2 | 64 位 | 2 |
| double / int64 / **指针** | 64 位 | 2 |
| **float4** | 128 位 | **4** |

**为什么指针是 64 位？**

GPU 有独立的虚拟地址空间，规模远超 32 位能表示的 4 GB。
CUDA 用统一虚拟寻址（UVA），所以设备指针固定 8 字节。
实测：`sizeof(void*) == 8`。

> **注意：即使你的卡只有 4 GB 显存，指针也仍然是 64 位的。**
> 显存大小和地址宽度是两回事。
### 地址空间比显存大得多，这正常吗？

**正常，而且这是理解「地址」的关键。**

实测（`phase0/cuda/addr_demo.cu`）：

```
显存实际大小          : 4.3 GB
cudaMalloc 拿到的地址 : 30113005568 = 30.1 GB   <- 比显存大 7 倍
这个地址需要多少位    : 35 位                    <- 32 位根本装不下
64 位地址空间上限     : 16 EB
```

**地址是一个「编号」，不是「显存里的位置」。**

比喻：图书馆。

| 计算机里的东西 | 图书馆里的对应物 |
|---|---|
| 数据 | 书 |
| 显存容量（4 GB） | 图书馆实际有多少本书 |
| 地址（30.1 GB 这个数） | 一本书的索书号 |
| 地址空间上限（16 EB） | 编号方案最多能编多少本 |

图书馆只有 200 本书，索书号照样可以写成 `A-0001234-56` 这么长。
**编号长，不代表书多。编号方案的大小和藏书量完全无关。**

**为什么编号要这么长？**

1. **32 位不够用**：实测你的地址需要 35 位。32 位最多编到 4 GB，
   连你这块卡自己的地址都表示不了。
2. **统一虚拟寻址（UVA）**：CPU 内存、GPU 显存、其他设备内存共用同一个地址空间，
   必须留足范围。
3. **虚拟内存的灵活性**：程序看到的是虚拟地址，硬件负责映射到真实位置。
   留出大量空编号，方便做映射、隔离、共享。

**「装地址的寄存器比显存还大」是误解**

寄存器里装的是**编号**，不是**显存**：

- 寄存器：2 格 x 4 字节 = **8 字节**，装一个编号
- 显存：**4 GB**，装数据

8 字节比 4 GB 小了几亿倍，**完全不离谱**。

「离谱」的感觉来自把「地址空间上限 16 EB」当成了「需要 16 EB 内存」。
恰恰相反：

> 编号方案预留了 16 EB 的范围，但**只有真正被用到的编号才对应物理内存**。
> 你的卡只用了编号 0 ~ 4 GB 那一段，其余 99.9999...% 的编号是空的，不占任何资源。

一句话：

> **地址是数字（标签），显存是东西（物品）。
> 数字能写多大，和有多少东西，是两件互不相干的事。**

### PTX 直接证据

命令：`nvcc -arch=sm_75 -ptx phase0/cuda/reg_demo.cu -o reg_demo.ptx`

PTX 是 nvcc 生成的"汇编"，寄存器类型是明写的：

```
.param .u64 ..._param_0,        <- 指针参数被声明成 64 位
.param .u32 ..._param_2         <- int 参数是 32 位

.reg .pred %p<2>;               <- 谓词寄存器（if 判断用）
.reg .f32  %f<13>;              <- 32 位浮点寄存器
.reg .b32  %r<6>;               <- 32 位整数寄存器
.reg .b64  %rd<8>;              <- 64 位寄存器，每个占 2 格
```

实际访存指令：

```
ld.global.v4.f32 {%f1, %f2, %f3, %f4}, [%rd5];
                   ^^^^^^^^^^^^^^^^      ^^^^^
                   4 格装数据             2 格装地址（64 位）
```

一条加载指令，**4 格装数据 + 2 格装地址**。

### 易错点：PTX 的寄存器是"虚拟"的

PTX 里 `.reg` 声明的是**虚拟寄存器**，数量不限。
ptxas 再把它们映射到真实的 32 位物理寄存器堆上，映射时会做复用和回收。

所以**PTX 里数出来的寄存器数会大于 ncu 报的最终值**，两者不能直接比。
（上面这个 kernel，PTX 声明了 13 + 6 + 8x2 = 35 个，但实际分配会少得多。）

> 这个"16"不是我编的：实测 FP32 峰值 2.76 TFLOP/s 反推出来每 SM 是 64 个 FP32 通道，
> 除以 4 个工位组 = 16。如果每个工位组有 32 个通道，峰值应该是 5.9 TFLOP/s，对不上。

### 加法任务到底要几格寄存器？——寄存器不是仓库，是托盘

**先把那个反直觉的疑问摆正：**

> "寄存器那么小，怎么可能装得下全部数据？"

**装不下，也从来不需要装下。** 这个问题的前提就错了。

数据的大本营从头到尾都是显存。寄存器只是个**掌心大的托盘**，放的是
"下一步马上就要加工的那几个零件"。数据是**流过**寄存器的，不是**存**在寄存器里的。

#### 场景图：数据在哪，托盘在哪

```text
   厂外大仓库 DRAM  4 GB                    车间 register file  256 KB/SM
   +------------------------------+        +------------------------+
   |  a[0 .. 64M)    256 MB       |        |     +-------+          |
   |  b[0 .. 64M)    256 MB       |  ==>   |     | 托盘  |  18 格   |
   |  c[0 .. 64M)    256 MB       | 传送带 |     +-------+          |
   +------------------------------+ (L2/L1)+------------------------+
          768 MB 全部数据在这儿                    只放手上这道工序要用的
```

| | 容量 | 装什么 |
|---|---|---|
| 一个车间的寄存器池 | 65536 格 x 4 B = **256 KB** | 正在被加工的值 |
| 14 个车间合计 | **3.5 MB** | |
| 厂区中转仓 L2 | 1 MB | 最近用过的数据 |
| 显存 DRAM | **4 GB** | 全部数据 |

**寄存器池只有显存的 0.086%。** 这不是缺陷，是整个体系能成立的前提：
**正因为装不下，才需要 L1 / L2 / DRAM 这套层级，把数据一车一车运到工位旁边。**

炒一道菜，你不会把整个冰箱搬上灶台，只把这一道菜要用的三样拿到手边。
CPU 也是同一个设计——全世界没有一台机器能把主存塞进寄存器。

#### 实测：这个加法任务到底几格

命令（`-cubin` 只编设备端代码，所以不需要 MSVC / vcvars）：

```powershell
nvcc -arch=sm_75 -cubin -Xptxas -v -o phase0/cuda/vecadd.cubin phase0/cuda/vecadd.cu
```

ptxas 报出来：

| kernel | 每线程寄存器 | spill |
|---|---|---|
| `init_data` | 12 | 0 |
| `vecadd_naive`（每线程 1 个 float） | **12** | 0 |
| `vecadd_float4`（每线程 4 个 float） | **18** | 0 |

每线程处理的数据量差了 4 倍，寄存器只差 6 格。**这个数字和"数据总量"没有关系。**

#### 真正的规律：看"同时活着的值"，不看"数据总量"

决定寄存器数的是 **同时活着的值的最大个数**（max live set）。
不是"这个任务一共要处理多少数据"，也不是"代码里出现过多少个变量"。

`vecadd_naive` 一个线程的完整一生只有两行：

```cuda
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) c[i] = a[i] + b[i];
```

把"同一时刻必须同时记住的东西"列出来：

| 必须同时记住的东西 | 格数 |
|---|---|
| 索引 `i` | 1 |
| `a` 的地址（64 位） | 2 |
| `b` 的地址（64 位） | 2 |
| `c` 的地址（64 位） | 2 |
| `a[i]` 读回来的值 | 1 |
| `b[i]` 读回来的值 | 1 |
| 结果 `a[i] + b[i]` | 1 |
| 记账：栈指针、字节宽度常量 | 2 |
| **上界合计** | **12** |
| **ptxas 实际分配** | **12** |

**手动数的和真机报的一模一样，12 格。** 关键一句：

> 数组是 256 MB 还是 256 GB，这个数**都是 12**。
> 数组大小只决定"派多少个工人"，不决定"一个工人手上同时拿几样东西"。

#### `float4` 版为什么只多 6 格（SASS 实证）

每个线程处理的数据从 4 字节变成 16 字节（4 倍），寄存器却只从 12 涨到 18（+50%）。
因为**固定开销（地址 + 索引 + 记账）占了大头，而它和处理几个元素基本无关。**

同样手数一遍：

| 必须同时记住的东西 | 格数 |
|---|---|
| 索引 `i` | 1 |
| `a` / `b` / `c` 三个地址 | 2 + 2 + 2 = 6 |
| 字节步长常量 16 | 1 |
| `x = a[i]`（float4） | 4 |
| `y = b[i]`（float4） | 4 |
| 记账：栈指针 | 1 |
| **上界合计** | **17 ~ 18** |
| **ptxas 实际分配** | **18** |

`cuobjdump -sass` 里能直接看到这些格子在干活：

```text
LDG.E.128.CONSTANT.SYS R8,  [R2] ;   读 a[i] -> 一次性占 R8 R9 R10 R11 四格
LDG.E.128.CONSTANT.SYS R12, [R4] ;   读 b[i] -> 一次性占 R12 R13 R14 R15 四格
FADD R11, R11, R15 ;                 y.z = x.z + y.z，原地覆盖，不额外占格
FADD R10, R10, R14 ;
FADD R9,  R9,  R13 ;
FADD R8,  R8,  R12 ;
STG.E.128.SYS [R6], R8 ;             写 c[i] -> 四格一起写出去
```

看两件事：

1. `LDG.128` 一条指令就把 4 格写满——这就是"每线程处理 4 个 float"在硬件上的样子。
2. `FADD` 的结果**原地覆盖输入**（`R8 = R8 + R12`），所以加法本身**一格都不多占**。
   这是编译器在做寄存器复用。

**所以规律是：**

> 寄存器用量 = 固定开销 + 同时活着的数据量
> 固定开销（索引、地址、常量，约 10 格）与"处理几个元素"几乎无关，
> 所以"数据量翻 4 倍，寄存器翻 4 倍"是错的直觉。

#### 澄清：寄存器当然装数据，它同时装地址和数据

前面说"寄存器只放马上要加工的零件"，很容易读成"寄存器只装地址"。**不是。**

> **数据本身就在寄存器里。** 你的 `a[i] + b[i]` 这个加法，就是在寄存器之间做的。
> FP32 运算通道（工作台）的输入和输出**都只能是寄存器**，不能直接对着显存算。

更准确的说法是：**寄存器格子是中性的容器，装什么由指令决定。**
同一个格子，加载前装地址，加载后装数据——`vecadd_naive` 的 SASS 里能直接看到这次"改行"：

```text
IMAD.WIDE R2, R6, R7, c[0x0][0x160] ;   R2:R3 = a 的地址(编号)   <- 此刻装的是地址
IMAD.WIDE R4, R6, R7, c[0x0][0x168] ;   R4:R5 = b 的地址(编号)   <- 此刻装的是地址
LDG.E.CONSTANT.SYS R3, [R2] ;           R3 = a[i]               <- 同一格, 装数据了
LDG.E.CONSTANT.SYS R4, [R4] ;           R4 = b[i]               <- 同一格, 装数据了
FADD R9, R4, R3 ;                       R9 = a[i] + b[i]        <- 纯数据
STG.E.SYS [R6], R9 ;                    把 R9 里的数据写出去
```

看 `R3` 和 `R4`：**一个字都没改，内容换了。** 先当"门牌号"被 `LDG` 用掉，
紧接着原地装上从显存取回的货。所以硬件里根本没有"地址寄存器"和"数据寄存器"两种东西，
只有 32 位格子，装什么取决于当前那条指令拿它当编号还是当数值。

那 12 格的真实分工：

| 用途 | 用哪几格 | 格数 |
|---|---|---|
| 装**地址**（编号） | R2:R3, R4:R5, R6:R7 | 6 |
| 装**数据**（数值） | R3, R4, R9 | 3 |
| 记账（栈指针、字节步长 4） | R1, R7 | 2 ~ 3 |
| **合计** | | **12** |

**那为什么 `naive` 版看着像"地址比数据还多"？**
因为它每线程只处理 **1 个**元素，数据只有 3 格；而三个 64 位地址是固定成本，要 6 格。

> **地址开销是常数级的（约 6~10 格，取决于几个指针），数据开销正比于每线程处理量。**
> 每线程 1 个 float 时地址占大头；每线程 4 个 float 时数据就追平了。

换成 `float4`，数据立刻从 3 格涨到 8 格（x 占 4 + y 占 4），地址还是 6 格，总共 18 格。

#### 所以"装不下"到底是什么意思

| | 格数 |
|---|---|
| 整个数组 a（64M 个 float） | **6400 万**格 |
| 一个线程的托盘 | **18** 格 |

差 **350 万倍**。寄存器装的是**正在算的那一份数据**，不是**整个数组**。
数据必须"排队过关"：

```text
显存 DRAM  ->  L2  ->  L1  ->  寄存器  ->  工作台算  ->  寄存器  ->  写回
   4 GB        1 MB    96 KB*   18 格/线程       FP32         结果
   (* L1 与 shared memory 共用这块 96 KB)
```

在这条链上，寄存器是**离工作台最近、但也最小**的一站。它不需要大，
因为它的任务只是"让工作台下一步有东西可算"。

#### 回到最初的问题：托盘装不下，为什么还够用

| | 数量 |
|---|---|
| 这次任务总共要处理的数据 | **768 MB** |
| 每个线程"手里"同时拿的数据 | **12 字节** |
| 每个线程的托盘容量 | 18 格 x 4 B = **72 字节** |

72 字节的托盘装 12 字节的活，**绰绰有余**。

问题不是靠"更大的寄存器"解决的，是靠**分工**解决的：
不是让一个工人装下 768 MB，而是让 6400 万个工人每人只装 12 字节。

> 寄存器不需要装下全部数据，就像收银员不需要装下整个超市的商品。
> 他手边只要有"正在扫的这一件"就够了。

#### 附带一条：寄存器不够时会怎样（spill）

上面三行都写着 `0 bytes spill stores, 0 bytes spill loads`——这叫**零溢出**。

假如某个 kernel 要用的寄存器超过上限，ptxas 只能把装不下的值**临时挪到显存**，
这叫 **spill（溢出）**。类比：工人托盘放不下了，只好把零件先搁到车间外面的地上，
用的时候再跑出去拿——**慢好几倍**。

所以看到 ptxas 报的 spill 不为 0，基本说明：

- 每线程处理的数据设计得太贪心，或者
- 该用 shared memory 暂存的没暂存

这是阶段 1 优化 GEMM 时要盯的第一批数字之一。

#### 怎么自己查（两条路）

| 方法 | 命令 | 看什么 |
|---|---|---|
| ptxas 直接报 | `nvcc -arch=sm_75 -cubin -Xptxas -v ...` | `Used N registers` + spill |
| ncu 看运行时 | `ncu --metrics launch__registers_per_thread ...` | 真机实际分配 |
| 看汇编 | `cuobjdump -sass phase0/cuda/vecadd.cubin` | 每条指令用了哪几格 |

手数的话，规矩只有一条：**数"同一时刻必须同时活着的值"，不数"代码里的变量"。**

## 一·补 随堂解释：SASS / L1 / 共享内存

收到"每次都冒出很多新名词"的反馈，这一节专门补课。

> **规矩（从现在开始执行）：每个新名词第一次出现，都要给"英文全称 + 一句白话"。**
> 之前 PTX、SASS、L1、shared memory、spill、coalesced 这些词都是直接甩出来的，
> 是我的问题。

### 1. SASS 是什么

你在 `.cu` 里写的代码，要经过**三次翻译**才能变成芯片听得懂的东西：

| 层 | 是什么 | 比喻 | 谁能读 |
|---|---|---|---|
| **CUDA C++** | 你写的 `.cu` 源码 | **中文草稿** | 人 |
| **PTX** | 一种"通用汇编"，nvcc 把 CUDA 翻成它 | **世界语译本** | 所有代际的 NVIDIA 卡都认 |
| **SASS** | "方言机器码"，ptxas 再把 PTX 翻成它 | **本地话定稿** | **只有这个型号的芯片认** |
| 机器码 | SASS 再往后就是 0 和 1 | 电信号 | 芯片 |

一句话：

> **PTX 是"通用说明书"，SASS 是"这台机器的方言"。**
> 换一张新显卡，CUDA 源码不用改，PTX 也还能用，但 SASS 必须重新生成。

名字的来历：

| 缩写 | 英文全称 | 中文 | 白话 |
|---|---|---|---|
| PTX | **P**arallel **T**hread e**X**ecution | 并行线程执行（虚拟指令集） | NVIDIA 定义的"通用汇编" |
| SASS | **S**hader **ASS**embly（社区展开，官方没给全称） | 着色器汇编 | "真·机器码"的可读形式 |
| ptxas | **PTX AS**sembler | PTX 汇编器 | 把 PTX 翻成 SASS 的程序，**寄存器分几格是它定的** |
| nvcc | NVIDIA CUDA Compiler | CUDA 编译器驱动 | 一条龙调度整条翻译链 |
| cuobjdump | CU object dump | CUDA 目标文件拆解工具 | 把编译好的程序拆开，打印 SASS 给人看 |

所以之前 `nvcc -Xptxas -v` 报的 18 格，就是 **ptxas 这个翻译官说"我给这个 kernel 分了 18 个格子"**。

三条命令对照：

```powershell
nvcc -arch=sm_75 -ptx   <源文件> -o out.ptx     # 只翻译到 PTX（通用版）
nvcc -arch=sm_75 -cubin <源文件> -o out.cubin   # 一路翻译到 SASS（方言定稿）
cuobjdump -sass out.cubin                       # 把 SASS 打印出来看
```

### 2. L1 不是寄存器，是完全不同的两样东西

**不是。** 这是两个**物理上分开**的存储块，容量、归属、谁管理都不一样。

把车间放大看：

```text
   一个车间（SM）
   +-----------------------------------------------+
   |   工人（线程）x 1024                           |
   |      [托盘 18 格]  <- 寄存器：人手一份，私有     |
   |          |                                     |
   |      +---------+                               |
   |      | 货架    |  <- L1 / 共享内存：全车间共用   |
   |      +---------+                               |
   +----------|------------------------------------+
              |  车间大门
   ===========|=================================== 厂区中转仓  L2   1 MB
              |
        厂外大仓库  DRAM  4 GB
```

| | 寄存器 | L1 缓存 |
|---|---|---|
| 工厂比喻 | 工人手边的**托盘** | 车间中间的**自动货架** |
| 私有还是共享 | **每个工人一份**（私有） | **全车间共用** |
| 谁管它 | **编译器 ptxas**，编译期就分好，写死在指令里 | **硬件自动**，运行时自己决定放什么、扔什么 |
| 本机容量 | 每 SM 256 KB，切给每个线程 18 格 | 与共享内存共用一块 **96 KB** 片上 SRAM |
| 速度 | 最快，工作台直接读（0 步） | 快，但比寄存器慢一档（走两步） |
| 程序员控制力 | **强**：改代码能影响用几格 | **弱**：只能"希望它命中"，没法直接指定 |

**为什么 L1 和共享内存老是一起出现？**
在 Turing（就是本机的 sm_75）上，L1 缓存和共享内存**是同一块物理 SRAM 切出来的**：
每个 SM 有 96 KB，你可以把大部分划给"自动货架"（L1），
也可以划给"程序员自己管的货架"（共享内存）。

本机 API 报的 `shared mem per SM 64 KB`，意思是**最多能划 64 KB 给共享内存**，
剩下约 32 KB 当 L1 缓存。（这就是刚才我把 L1 写成 128 KB 是错的、已经改掉的原因。）

> 一句话记住：
> **寄存器是"手上的"，L1 是"车间里的"。**
> 从手到车间两步，从车间到厂区中转仓几十步，到厂外大仓库几千步。
> 整个存储层级存在的意义，就是让"走得少"的层尽量接住"要走远"的访问。

## 三、最要命的概念：距离

瓶颈往往不是"工作台够不够"，而是**取料要走多远**。

| 存东西的地方 | 英文 | 比喻 | 走一趟 |
|---|---|---|---|
| 寄存器 | register | 工人专属的储物格（在车间柜子里） | 0 步，伸手就有 |
| 共享内存 | shared memory | 车间中间的货架 | 几步 |
| 二级缓存 | L2 cache | 厂区中转仓 | 几十步 |
| 显存 | DRAM / global memory | 厂外大仓库 | **500 步** |

规律：**离工作台越近的越小越贵，越远的越大越慢。**
vecadd 慢就慢在：每加工一个零件都要跑一趟 500 步的厂外仓库。

## 四、warp：32 个工人编成一个班组

传送带是 **32 个工人的任务一起送**，所以工人被编成 32 人一组，
这个组合叫 **warp（线程束）**。

铁律：**齐步走。** 班长喊"加"，32 个人**同时**加；喊"搬"，32 个人**同时**搬。
一条口令，全班一起动 —— 这就是 GPU 能用一条指令驱动 32 个线程的原因
（术语叫 **SIMT**，Single Instruction Multiple Threads，单指令多线程）。

代价：32 个人里如果有几个要干别的活，班长只能让**全班停下等他们**。
术语叫 **warp divergence（线程束分叉）**，效率杀手。

> 比喻：军训方阵。谁要单独行动，整个方阵就得为他停下。

**注意**：上一条说一个班组 32 人，但工位组只有 16 个工作台，
所以一条口令实际是**分两批**完成的。这不影响"齐步走"的结论，
只是说明一个班组占两个周期。

---

## 五、班长（warp scheduler）

每个工位组配 **1 个班长**，术语叫 **warp scheduler（线程束调度器）**。
他手下最多管 **8 个班组**（8 x 32 = 256 个工人）。

班长的规则：**每一回合只能喊一条口令**（术语叫 **issue，发射**）。

所以他的活是：从 8 个班组里挑一个"此刻真的能干活"的，喊口令。
挑不出人来的情况叫 **stall（停顿）**。

现在之前那些 ncu 数字就有画面了：

| ncu 指标 | 英文原名 | 翻译成人话 |
|---|---|---|
| 7.60 / 8 | Active Warps Per Scheduler | 班长手下有 7.6 个班组，人手管够 |
| 0.03 | Eligible Warps Per Scheduler | 但这一刻只有 0.03 个班组"手上有料能干活" |
| 97.16 % | No Eligible | 97% 的回合，班长喊不出任何口令 |
| 268 周期 | Warp Cycles Per Issued Instruction | 全班平均等 268 个周期才轮到下一条口令 |

**8 个班组全都站着，但都在等料，班长干着急。**

## 六、占用率（occupancy）= 车间入住率

车间里能住几个班组？三个限制，取最小的那个：

| 限制 | 英文 | 比喻 | 额度 |
|---|---|---|---|
| warp 槽位 | max threads per SM | 车间的床位 | 32 个班组 |
| 寄存器 | register file | 每个工人占的储物格数 | 65536 格 |
| 共享内存 | shared memory | 车间货架面积 | 64 KB |

```
occupancy（占用率）= min(三条限制各自算出的班组数) / 32
```

**为什么希望住得满？** 班组越多，班长越有可能找到"手上有料"的那个。
住得少、大家又都在等料，班长就只能空转。

vecadd：每个工人只用 18 个储物格 -> 算下来能住 113 个班组 ->
**但床位只有 32 个** -> 住满。所以 block size 怎么调都一样。

## 七、为什么 14 个车间就能"打满"厂外仓库

厂外仓库全厂共用一个，它同时能处理的"取料单"有上限。

> 比喻：**仓库门口只有一个装卸口。**
>
> - 只派 1 个跑腿的出去 -> 装卸口大部分时间空着（带宽没用满）
> - 派 112 个跑腿的出去 -> 装卸口一刻不停（带宽打满）
> - 派 1 万个跑腿的 -> **装卸口还是那个速度，多出来的全在排队**

所以"需要多少并行度"的答案不是"每个车间要有多少活"，
而是"**同一瞬间有多少张取料单在路上**"。
术语叫 **memory-level parallelism（内存级并行）**。

算一下：仓库一趟 500 步，要满负荷需要约 **107 KB 的货同时在路上**。
112 个班组一轮能凑 57 KB，再叠加每个班组同时挂几张单子，够用。
**所以 14 个 block 就够，加更多只是排队。**

## 九、用这个比喻重新理解「合并访存」

班长喊"去仓库取料"，32 个工人各自报一个货位号。

- **合并**：报的是 0、1、2、……、31 -> 全在同一个货架区挨着 -> 跑腿的**一趟全搬回来**
- **不合并**：报的是 0、1024、2048、…… -> 散落在 32 个角落 -> **必须跑 32 趟**，
  每趟只拿一小件

仓库的规矩是"来一趟至少搬 32 件的量"。所以散着拿时，
**32 趟里有 31/32 的搬运是白费的**。这就是 coalesced 的全部含义。

## 十、最反直觉的一条

你写 CUDA 代码时，感觉是在给"每一个工人"下指令。但实际是：

- 工厂不听你指挥工人，**工厂只认班组**
- 你写"5 号工人做这个、6 号工人做那个"，工厂自动把 0-31 号编成第一班、
  32-63 号编成第二班
- 班长喊口令时，**全班一起动**

所以你唯一能影响"班组怎么站队"的办法，就是**给工人编号的方式**。
同样的 32 个工人，编号方式不同，队形就不同，去仓库的路线也不同。

**这就是为什么 `threadIdx.x` 怎么写，会直接决定性能。**

> 一句话：**你写的是"每个工人"的逻辑，跑的是"班组 + 车间"的物理。
> 性能问题几乎都来自两者的错位。**

## 十一、从线程到硬件的完整映射链

这条链是整个 GPU 编程的地基，建议背下来。

```
你启动 1024 个 thread（工人）
    |
    |  硬件按 32 个一组打包
    v
32 个 warp（班组），每个 warp = 32 个工人
    |
    |  分配到 14 个车间（SM）上
    v
每个车间最多装 32 个班组 = 1024 个工人
    |
    |  每个车间分成 4 个工位组（SMSP）
    v
每个工位组配 1 个班长，管 8 个班组（8 x 32 = 256 个工人）
    |
    |  班长每周期只能喊 1 条口令
    v
从 8 个班组里挑 1 个能干的 -> 喊口令 -> 那 32 个工人一起动
    |
    |  但工位组只有 16 个工作台
    v
一条口令分两批执行完
```

本机实测对照：

| 环节 | 数值 | 来源 |
|---|---|---|
| warp 宽度 | 32 threads | cudaDeviceProp.warpSize |
| 每车间工人上限 | 1024 | maxThreadsPerMultiProcessor |
| 每车间班组上限 | 32 | 1024 / 32 |
| 每车间工位组数 | 4 | ncu 的 SMSP/SM 周期比 = 4.0 |
| 每组班长管几个班组 | 8 | 32 / 4 |
| 每组工作台数 | 16 | 64 FP32/SM 除以 4 |

最后一行正是 ncu 里 `Active Warps Per Scheduler 7.60 / 8` 的分母。

## 十三、数字对账：理论 vs 实测

| 项目 | 理论值 | 实测值 | 效率 |
|---|---|---|---|
| 显存带宽 | 192.0 GB/s | 179 GB/s | 93 % |
| FP32 算力 | 2.96 TFLOP/s | 2.76 TFLOP/s | 93 % |
| Roofline 转折点 | 15.4 FLOP/byte | 15.4 | -- |

理论值怎么来的：

- 带宽 = 总线位宽/8 x 显存时钟 x 2 = 128/8 x 6001 MHz x 2 = 192 GB/s
- 算力 = 通道数 x 2（一个 FMA 算两次浮点运算）x 时钟
  = 896 x 2 x 1.65 GHz = 2.96 TFLOP/s

**93% 不是巧合，是常态：理论峰值永远达不到，能到 90% 以上就算健康。**
以后看到"实测只有理论值的 93%"，先别怀疑有 bug。

## 十四、常见误解清单

这些是我踩过或差点被绕进去的坑，每个都记下来。

**1. "工人"不能同时指线程和运算单元**

我犯过这个错：写"32 人的班组"，又写"每组 16 个工人（FP32 核心）"，
结果 32 个人要坐进 16 个位置。

正确分法：**工人 = thread（虚拟）**，**工作台 = FP32 lane（真实）**。
两者的数量对不上是常态，必须分开命名。

**2. SM 利用率低不等于 SM 在闲着**

`Compute (SM) Throughput` 低有两种完全不同的原因：
- (a) 算得快，活儿一会儿就干完了
- (b) 卡住了，在等别的资源

区分方法：看总耗时。vecadd 跑了 4.5 ms，如果计算是瓶颈应该只花
`4.5 x 4.98% = 0.22 ms` -> 说明是 (b)，卡住了。

**3. 并行度不是越多越快**

仓库装卸口只有一个（带宽固定）。跑到饱和点之后，再加并行度只是排队。
实测：14 个 block 就打满，加到 16384 个只快 0.8%。

**4. block 越大不等于越快**

只有当 block size 影响到占用率时才有关系。
vecadd 用 18 个寄存器、0 共享内存，64~1024 全都是 100% 占用率，所以完全无差别。

**5. 理论峰值是达不到的**

93% 已经算健康。看到"只有 93%"先别怀疑。

**6. thread 不是真实硬件**

硬件里只有 warp。你写的"每个线程独立执行"是幻觉，
SIMT 下 32 个线程共享一个程序计数器。

**7. 更差的写法不一定更慢**

float3 的指令数是 float4 的三倍，实测一样快 —— 因为瓶颈在 DRAM，
而它没有增加 DRAM 搬运量。**优化前先确认你要优化的资源不是闲置的。**

## 十五、ncu 指标速查卡

拿到一个 kernel，按这个顺序看：

| 序号 | 看什么 | 指标名 | 怎么判断 |
|---|---|---|---|
| 1 | 谁是瓶颈 | `DRAM Throughput` vs `Compute (SM) Throughput` | 谁高就是谁 |
| 2 | 带宽利用率 | `DRAM Throughput` | > 80% 说明带宽快满了 |
| 3 | 算力利用率 | `Compute (SM) Throughput` | > 80% 说明算力快满了 |
| 4 | 访存有没有浪费 | `L1/TEX Hit Rate`、`Sectors per Request` | 命中率低 + 请求数多 = 访存没合并 |
| 5 | 人手够不够 | `Achieved Occupancy` | 低于 50% 要查寄存器和共享内存用量 |
| 6 | 班长忙不忙 | `No Eligible` | 高说明班组都在等料 |
| 7 | 在等什么 | `Warp State` 里的 stall 原因 | 看占比最大的那一项 |
| 8 | 线程有没有掉队 | `Avg. Not Predicated Off Threads Per Warp` | 明显小于 32 说明有分叉或边界掩码 |

**最常用的一条判断**：

> `DRAM > 80%` 且 `Compute < 20%` -> 纯访存瓶颈，别再优化指令了，
> 除非能**减少访存总量**（融合 kernel、降精度、复用数据）。

vecadd 就落在这个区间：DRAM 93.31%，Compute 4.98%。
