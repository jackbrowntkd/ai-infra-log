# 概念笔记 02 · GPU 硬件架构与 CUDA 编程模型

所有数字来自 `phase0/cuda/device_query.exe` 在本机的实测输出。

---

## 一、层级结构

```
T600 Laptop GPU
├── 显存 4 GB GDDR6      128-bit 总线，理论 192 GB/s
├── L2 Cache  1 MB        全芯片共享
└── 14 x SM               芯片上重复 14 份，彼此独立
     ├── 4 x SMSP（处理块）
     │    ├── 16 x FP32 核心
     │    ├── LD/ST 单元（负责发访存请求）
     │    ├── SFU（sin / exp 等特殊函数）
     │    ├── 寄存器堆
     │    └── 1 x Warp Scheduler  每个周期从这里管的 warp 里挑 1 个发射指令
     ├── 64 KB 共享内存 / L1
     └── 没有 Tensor Core（TU117 特有，和 GTX 16 系同源）
```

**关键点：14 个 SM 是彼此独立的重复单元。** 它们不共享寄存器、不共享共享内存。
共享的只有 L2 和显存。

### 用你自己的 ncu 数据验证「4 个 SMSP」

```
Total SMSP Elapsed Cycles   948,984
Total SM Elapsed Cycles     237,246
948984 / 237246 = 4.0
```

正好 4 倍，证明每个 SM 内部确实分 4 个处理块。

### CUDA API 不告诉你的东西

`cudaDeviceProp` 只暴露「每个 SM」级别的信息。它**不会**告诉你每个 SM 里有多少个
FP32 核心、多少个 LD/ST 单元。所以 device_query.cu 里那个 896 是**推出来的**：
14 SM x 64（Turing 每 SM 64 个 FP32），再用实测峰值 2.76 TFLOP/s 反向验证。

## 二、从线程到硬件的映射链

这条链是整个 GPU 编程的地基，值得背下来：

```
你写了 1024 个 thread
   ↓  硬件按 32 个一组打包
32 个 warp（每个 warp = 32 个 thread）
   ↓  分配到 14 个 SM 上
每个 SM 最多装 32 个 warp（= 1024 threads）
   ↓  每个 SM 分成 4 个调度器
每个调度器管 8 个 warp
   ↓  每个周期
从 8 个里挑 1 个能干的，发射 1 条指令 → 那 32 个线程一起执行
```

本机实测对照：

| 环节 | 数值 |
|---|---|
| warp size | 32 threads |
| threads per SM | 1024 |
| warps per SM | 32 |
| 调度器数 | 4 |
| 每调度器管几个 warp | 8 |

最后一行正是 ncu 里 `Active Warps Per Scheduler 7.60 / 8` 的分母。

## 三、warp 是什么

**比喻：军训方阵。**

SM 的执行单元是 **32 个车道宽**的数据通路，一次只能给一个 32 人方阵下口令。
方阵里的士兵必须**齐步走** —— 同一条指令，每人操作自己那份数据。

- 32 个人一起做加法 → 1 条指令，32 次运算
- 如果有人要去做别的事（`if-else` 分叉）→ **两队分开走**，一队走时另一队干等
  这就是 **warp divergence**，是性能杀手

要点：

- warp 是硬件**调度和执行的最小单位**，1 条指令 = 32 个线程同时动
- **你没法直接创建或控制 warp。** 你只写 thread 的代码，硬件负责打包

## 四、寄存器与占用率

每个 SM 有 **65536 个寄存器**，这是它的「预算」。

```
一个线程用 R 个寄存器
  -> 一个 warp 用 32R 个
  -> 能装的 warp 数 = min(32, 65536 / 32R) = min(32, 2048 / R)
```

vecadd 每线程用 18 个寄存器：`2048 / 18 = 113`，远大于 32 → 被 32 卡住
→ **理论占用率 100%**。

这直接解释了为什么 block size 从 64 到 1024 完全无差别：
**每一种配置都能把这 32 个 warp 槽位填满。**

什么时候寄存器才会成为限制？

| 每线程寄存器数 | 能装的 warp | 占用率 |
|---|---|---|
| 18 | 32（上限） | 100 % |
| 40 | 32（上限） | 100 % |
| 68 | 30 | 94 % |
| 128 | 16 | 50 % |

---

## 五、决定占用率的三个预算

| 资源 | 每 SM 预算 | 用尽的后果 |
|---|---|---|
| warp 槽位 | 1024 threads = 32 warps | 硬上限 |
| 寄存器 | 65536 | 每线程寄存器越多，能装的 warp 越少 |
| 共享内存 | 64 KB | 每个 block 要得越多，能装的 block 越少 |

```
占用率 = min(三条限制各自算出的 warp 数) / 32
```

| 项目 | 理论值 | 实测值 | 效率 |
|---|---|---|---|
| 显存带宽 | 192.0 GB/s | 179 GB/s | 93 % |

# 硬件 vs CUDA 编程模型

## 对应表

| CUDA 里的概念 | 硬件里对应什么 | 一一对应？ |
|---|---|---|
| thread | **没有这个东西** | 纯粹抽象 |
| warp | 32 宽的执行单元 | 硬绑定 |
| block | 一组同时驻留的 warp | 松 |
| grid | 整个 GPU | 松 |
| shared memory | SM 里的物理 SRAM | 物理存在 |
| `__syncthreads()` | block 内屏障 | 因为 block 保证同驻一个 SM 才有意义 |
| SM | 硬件 | 编程模型里不暴露 |

## 五个关键区别

### 1. thread 是虚构的

硬件里没有「线程」这个对象。一个线程 = 一套寄存器 + 一个 PC 槽位。
而且 SIMT 下 32 个线程**共享一个 PC**。
「每个线程独立执行」是幻觉，**只有 warp 是真实的**。

### 2. block 保证「同时驻留」，但不保证位置

CUDA 的保证是：同一个 block 的所有线程**一定同时活着**（要么全上，要么全不上），
并且**在同一个 SM 上**。这就是 `__syncthreads()` 和 shared memory 能工作的原因。

但你不该假设 block 落在哪个 SM，也不该假设多个 block 的相对顺序。

### 3. 你控制不了 warp，只能间接影响它

硬件按 `threadIdx` 的线性顺序，每 32 个切一个 warp。所以：

```cuda
// 好：threadIdx.x 连续 -> warp 内地址连续 -> coalesced
c[i] = a[i] + b[i];

// 坏：跨步 2 -> warp 内地址跳跃 -> uncoalesced
c[i * 2] = a[i * 2] + b[i * 2];
```

**索引的写法直接决定 warp 的访存形状**，这是程序员影响 warp 的唯一途径。

### 4. grid / block 的维度是纯逻辑的

`dim3` 的 1D/2D/3D 只是让索引方便。硬件只看到一长串线性的 warp。
而且 **block 的执行顺序完全不保证**，不能假设 block 0 先跑。

### 5. 同步的作用域不同

- `__syncthreads()` 只在 block 内有效 —— 因为只有 block 保证同驻
- 跨 block 同步必须靠：多次 kernel 启动、atomic、或 coop groups

## 一句话总结

> **你写的是逻辑模型（thread / block / grid），跑的是物理模型（warp / SM）。
> 性能问题几乎全部来自两者的错位。**

常见错位：

- 你以为「32 个线程各干各的」，硬件看到的是「32 个线程齐步走」-> warp divergence
- 你以为「每个 block 独立处理一块数据」，硬件把它们塞在同一个 SM 上抢资源
- 你以为「我启了 100 万个线程很厉害」，硬件在算「这 14 个 SM 的 32 个 warp 槽位装得下吗」
