# 笔记 05 · Roofline 模型：两条线为什么能定死性能上限

前置：`03_factory_analogy.md`（工厂术语）、`04_vecadd_walkthrough.md`（vecadd 全流程）。

这篇只回答两件事：**roofline 是怎么推出来的？凭什么说它一定成立？**

所有数字来自本机实测：`phase0/hardware.json`、`phase0/measured/vecadd.json`、
`phase0/reports/roofline.png`。推导是纸上的，每个结论都给实测点对账。

---

## 0. 一句话版本

> **算法决定你站在横轴的哪里（算术强度），硬件决定屋顶有多高（带宽 + 算力）。
> 性能一定在屋顶之下；离屋顶多远，才是实现问题。**

它之所以叫"模型"而不叫"经验公式"，是因为**不是拟合出来的**，
而是从上界推导出来的。下面的推导只用两个假设，没有一条依赖具体硬件。

---

## 1. 推导：三步，全是记账

先定义四个量。前两个属于**任务**，后两个属于**硬件**——
这个分工是整个模型能成立的关键。

| 符号 | 含义 | 单位 | 本机 / vecadd |
|---|---|---|---|
| `W` | 这次 kernel 要做多少次浮点运算 | FLOP | 67.1 MFLOP |
| `M` | 这次 kernel 要搬多少字节 | byte | 805 MB（768 MiB） |
| `P` | 算力峰值 | FLOP/s | 2760 GFLOP/s |
| `B` | 带宽峰值 | byte/s | 179 GB/s |

**第一步：两个资源各自"单独干完要多久"。**

```text
光靠算，至少   W / P   秒
光靠搬，至少   M / B   秒
```

**第二步：取较大的那个，而不是相加。**

```text
T >= max( W/P , M/B )
```

**第三步：性能 = 运算量 / 时间，把 W 挪到左边。**

```text
F = W/T <= W / max(W/P, M/B) = min( P , W*B/M )

令 AI = W / M  （算术强度，FLOP/byte），得：

F <= min( P , AI * B )
```

到此结束。**roofline 的全部内容就是最后这一行。**

各项分工一目了然：

| 项 | 由谁决定 | 变化时的影响 |
|---|---|---|
| `AI = W/M` | **算法**（数据复用程度） | 决定你在横轴上的位置 |
| `B` | 硬件（显存带宽） | 决定斜线多陡 |
| `P` | 硬件（算力峰值） | 决定水平线多高 |
| `P/B` | 硬件（机器平衡点） | 决定转折点在哪 |

---

## 2. 为什么它一定成立

`T >= max(W/P, M/B)` 成立的理由只有两句：

1. **活必须干完**：`W` 次运算一次都不能少，`M` 字节一字节都不能省；
2. **资源不能超速**：算力每秒最多 `P` 次，带宽每秒最多 `B` 字节。

注意这里**没有假设**两个资源能不能重叠：

- 如果重叠得**完美**（一边搬一边算），总时间就恰好是 `max(...)`；
- 如果经常互相等料，总时间是**相加**，只会**更大**。

所以 `max(...)` 是**最好情况下的下界**，性能上限因此是**铁上界**：
任何调度、并行度、编译器优化，都只能让点从下方**逼近**屋顶，
不可能穿出去。这就是它"成立"的确切含义。

**必须记住的推论**：`P` 和 `B` 是**峰值**，不是"通常能达到的值"。

| | 理论峰值 | 本机实测 | 效率 |
|---|---|---|---|
| 带宽 | 192.0 GB/s | 179 GB/s | 93 % |
| FP32 算力 | 2.96 TFLOP/s | 2.76 TFLOP/s | 93 % |

所以**屋顶是天花板，不是预测值**。能到 90% 以上就算健康（见笔记 03 第十三节）。

---

## 3. 为什么图形是"屋顶"

在 log-log 坐标下，`F = AI * B` 是一条**斜率 1 的直线**，
`F = P` 是一条**水平线**，可行区域在两者的**下方**，所以取**下包络**：

```text
性能 (log)                      <- 算力屋顶 P（水平线）
  |                  ┌────────────────────────────────
  |                ╱
  |              ╱    <- 屋顶 = 下包络：斜线 + 水平线
  |            ╱
  |          ╱        <- 带宽屋顶 AI*B（斜率 1）
  |        ╱
  +───────┴───────────────────────────────────────────→ AI (log)
       转折点 P/B
```

- **AI 小**（每字节工序少）→ 被斜线压住 → **带宽受限**
- **AI 大**（每字节反复加工）→ 被水平线压住 → **算力受限**
- 交点 `AI* = P/B` 叫**转折点**，也就是这台机器的"机器平衡点"

本机：`2760 / 179 = 15.42 FLOP/byte`，和 `device_query.txt` 里用理论值
算出的 `machine balance 15.4` 完全一致（因为实测和理论都是 93%，比值被约掉了）。

## 4. 工厂比喻（接着 03 讲）

沿用 `03_factory_analogy.md` 的角色，模型只有一句话：

> **看装卸口（带宽）和工作台（算力）哪个先忙不过来。**

厂外只有一个装卸口，每秒最多吐 `B` 件货；车间里 896 个工作台，每秒最多做 `P` 道工序。

> **算术强度 = 每搬进来一件货，在工作台上做几道工序。**

| | 装卸口 | 工作台 | 卡在哪 | 该优化什么 |
|---|---|---|---|---|
| **矩阵乘法** | 闲着 | 排队 | 水平线 | 指令、布局、减少指令数 |
| **向量加** | 排队 | 几乎全闲 | 斜线 | 减少搬运量，别碰指令 |

斜线的含义很直白：装卸口每秒只放得进 `B` 件货，每件货最多换来 `AI` 道工序，
所以**每秒最多 `B * AI` 道工序**——再多的工作台也没用，它们没料可加工。

"为什么取 max 不取相加"在工厂里也很自然：一批货在路上的同时，
另一批可以在工作台上加工（流水线重叠）。**完美重叠时**总时间取较长的那一个；
一旦两边互相等料，时间只会更长、点只会更低。屋顶描述的正是"最好的情况"。

转折点的物理含义：**装卸口的供料速度刚好够工作台吃满的那个工序数。**
低于它，工作台在等料；高于它，料在门口排队。

## 5. 逐元素读懂 `roofline.png`

图由 `phase0/roofline.py` 生成，输入是 `hardware.json` + `measured/*.json`。

| 图上的元素 | 是什么 | 怎么算出来的 |
|---|---|---|
| 横轴 **算术强度 (FLOP/byte)** | 算法的属性 | `AI = W / M`，log 刻度，范围 1e-2 ~ 2e3 |
| 纵轴 **性能 (GFLOP/s)** | 结果 | `W / T`，log 刻度，范围 1 ~ 5520 |
| 蓝线 **带宽屋顶 179 GB/s** | 斜线 | `F = AI * 179`，斜率 1；在 AI ≈ 31 处穿出画面顶部 |
| 红线 **算力屋顶 2760 GFLOP/s** | 水平线 | `F = 2760`，横贯全图 |
| 灰虚线 **转折点 15.4 FLOP/byte** | 两条线的交点 | `2760 / 179 = 15.42` |
| 两个点 **vecadd_naive / vecadd_float4_b256** | 实测 kernel | AI 都是 0.0833，实测 14.8 / 15.0 GFLOP/s |

**三条读图规则：**

1. **看点在谁旁边**：贴着蓝线 = 带宽受限，贴着红线 = 算力受限。
2. **看离屋顶的垂直距离**：那就是还剩多少优化空间。
3. **看能不能往右移**：提高 AI（数据复用）是唯一的"改命"手段，
   因为它能把点从斜线推到水平线的最低处——过了转折点再提 AI 就没用了。

> **一个已知的视觉小坑**：左上角的图例框有半透明白底（matplotlib 默认
> `framealpha=0.8`），把红线左段压成了淡粉色，看上去红线像是从图例右边才开始的。
> 实际它横贯全图（AI < 0.13 那一段被盖住）。不影响转折点和数据点，不用管。

## 6. 用本机数字走一遍（vecadd）

向量加是**极端的带宽受限**样本：搬 12 字节，只做 1 次加法。

| 量 | 值 | 出处 |
|---|---|---|
| 元素数 N | 64 Mi = 67,108,864 | `vecadd.cu`: `64 << 20` |
| 每数组 | 256 MiB | |
| 一次启动搬运 M | **805 MB**（768 MiB） | `3 * N * 4`（读 a + 读 b + 写 c） |
| 运算量 W | 67.1 MFLOP | 每元素 1 次加法 |
| 算术强度 | **1/12 = 0.0833** | `W / M` |

把 AI 代进屋顶：

```text
带宽屋顶给的上限 = 0.0833 * 179 GB/s = 14.9 GFLOP/s
算力屋顶给的上限 = 2760 GFLOP/s          <- 高 185 倍，完全没用上

实测 float4_b256：805 MB / 4.480 ms = 179.8 GB/s -> 15.0 GFLOP/s
实测 naive      ：805 MB / 4.539 ms = 177.4 GB/s -> 14.8 GFLOP/s
```

结论：**点在蓝线上（带宽用满 ~100%），离红线还有 185 倍（只占 0.54%）。**

四条交叉验证：

| 证据 | 数值 | 说明 |
|---|---|---|
| ncu `DRAM Throughput` | 93.31%（179.11 GB/s） | 相对**理论 192 GB/s** 的 93%，与硬件实测效率一致 |
| ncu `Compute (SM) Throughput` | 4.98% | 注意口径不同，见第 7 节「盲区 3」 |
| `membound_qa.md` EXP1 | float1/2/3/4 差异 < 0.25% | 被 DRAM 卡死时，指令数不构成约束 |
| `membound_qa.md` EXP3 | grid 从 14 加到 16384 只快 0.8% | 装卸口只有一个，加并行度只是排队 |

这几条能对上，就是因为 roofline 先判定了"卡在带宽"。
**先确定瓶颈在哪，再决定优化方向**——这就是阶段 0 要练的核心技能。

## 7. 四个盲区（别把模型用坏）

四条盲区分两类：**前两条是屋顶本身画得偏乐观，后两条是你的尺子没和屋顶对齐。**
总比喻：roofline 像一块限速牌加一张地图——它告诉你这段路最快能跑多少、
你在哪个路段，但不告诉你哪儿堵车，而且你得先确认自己的时速表单位不是英里。

### 盲区 1：屋顶是理想值，不是预测值

> **比喻：高速限速 120。** 限速是"这辆车在最好条件下最快能跑多少"，
> 不是"你这一趟能跑多快"。你照样可能堵在收费站。而且限速牌**不会告诉你堵在哪**。

`B = 179 GB/s` 是"一刻不停、每趟满载、单子多到装卸口不空转"的能力。
笔记 01 的 ncu 数据正是反面教材：`Active Warps 7.60/8`（人手足）、
`No Eligible 97%`（但全在等料）、`Warp Cycles Per Issued Instruction 268`（发一条令等 268 拍）
——**装卸口不缺人，缺的是同一瞬间在途的取料单**（笔记 03 第七节：要 14 个 block 才喂满）。

所以正确用法是分工：**roofline 先分方向（该优化算力还是带宽），ncu 再找距离和原因。**
另外别忘了屋顶本身就是天花板——93% 就算健康（第 2 节）。

### 盲区 2：`bytes` 指哪一级存储

> **比喻：快递的三段路。** "广州仓发到上海分拨中心"和"分拨中心送到你家门口"
> 都叫搬运，但车辆、时间、成本完全不同。**只统计出省的长途单，会误判"运力很闲"**
> ——实际可能是最后一公里的电动车不够。

四级存储（寄存器 ← L1/共享内存 ← L2 ← DRAM）**每一级都有自己的带宽上限**，
而标准 roofline 只画了**出省那一段（DRAM）**的屋脊。于是会出两种偏差：

- **偏乐观**：数据在缓存里反复用的 kernel（比如分块矩阵乘法），出省的长途单很少，
  按 DRAM 记账 `AI` 偏大、点被推到右边，模型以为"数据不要钱、可以冲算力峰值"。
  但它真正的瓶颈可能是**车间货架（共享内存 / L1）的带宽**——那条屋脊更低。
- **偏悲观**：反过来，如果流量里有一部分被缓存接住了却仍按 DRAM 记账，
  `AI` 会被低估，点被推到左边看着像"带宽受限"，其实还有空间。

**修法：分层 roofline。** 每一级存储各画一条屋脊线，**取最低的那条**，那才是真瓶颈。
阶段 1 的矩阵乘法分块就是典型：把货先拉到车间货架再从货架取，DRAM 账本很漂亮，
真正的约束在共享内存。**算 `AI` 之前先问一句："我统计的是哪一级的字节？"**

反过来说，vecadd 是干净的纯长途单：工作集 768 MiB 远大于 1 MB 的 L2，
数据没有在缓存里被接住。所以标准 roofline 对它完全适用——这也是它能贴着蓝线跑的原因。

> **别被 `L2 Hit Rate 33.33%` 骗了**：它**不是"三分之一的数据命中了缓存"**。
> ncu 的 `L2 Hit Rate` = `lts__t_sector_hit_rate.pct`，是"L2 sector（32 B）查询的命中比例"，
> 而**写满整个 sector 的 store 不需要先从 DRAM 取数，因此算命中**。实测分解：
>
> | 查询类型 | sector 数 | 命中 | 命中率 |
> |---|---|---|---|
> | 读 a / b | 16,794,312 | 5,313 | **0.03 %** |
> | 写 c | 8,390,349 | 8,388,672 | 100 % |
> | 合计 | 25,184,661 | 8,393,985 | **33.33 %** |
>
> 读写正好 2:1（每个元素读 16 B × 2 + 写 16 B），所以 1/3 只是
> **读写比例的镜像**，和"数据复用"毫无关系。**判断有没有复用要看
> `lts__t_sectors_op_read_lookup_hit`，不要看总的 L2 Hit Rate。**
> 旁证：`dram__bytes_read` = 536.91 MB（512 MiB）、`dram__bytes_write` = 268.36 MB（256 MiB），
> 合计正好是义务流量 805 MB —— 一分多余的搬运都没有。
>
> 完整原始输出见 `phase0/reports/sector_probe.txt`，展开推导见笔记 06。
>
> ```powershell
> ncu --metrics lts__t_sectors_op_read_lookup_hit.sum,lts__t_sectors_op_read_lookup_miss.sum,lts__t_sectors_op_write_lookup_hit.sum,dram__bytes_read.sum,dram__bytes_write.sum -k regex:vecadd_float4 .\phase0\cuda\vecadd.exe
> ```

### 盲区 3：两个百分数不是同一个口径

> **比喻：同一个班，一个老师说"及格率 95%"，另一个说"上课抬头率 5%"。**
> 两个数都不假，但一个数的是**产出**，一个数的是**节奏**。

- `0.54%` 是**产出**：实际做了 15 GFLOP/s，峰值能给 2760，只用了千分之五。
- `4.98%` 是**节奏**：调度器每个周期有一个发射槽位，实际只填了 5%。

差约 9 倍却不矛盾，原因在**指令构成**：vecadd 的指令里大部分在算地址和搬货，
真正做浮点的只有那几条 `FADD`；而且 `FADD` 一次只算 1 次运算，
峰值算力却是按 `FMA`（一次算 2 次）定义的。所以**就算把口令喊满 100%，
浮点产出也远到不了峰值**——这也正是笔记 03 里"SM 利用率低有两种原因"的那一条。

用哪个取决于你要回答什么：

| 你想回答 | 该看 | 为什么 |
|---|---|---|
| 谁是瓶颈 | ncu 的 `DRAM 93.31%` vs `Compute (SM) 4.98%` | 同一次采集、同源、可比 |
| 离 roofline 多远 | `0.54%`（15 / 2760） | 和屋顶的分母一致 |

两个场景别串着用，更**不能相减或相除**。

### 盲区 4：FLOP 怎么数

> **比喻：点菜时"一道菜"怎么算。** 宫保鸡丁算 1 道，还是算"炒、勾芡、装盘"3 道？
> 菜没变，你报的数字差 3 倍——而 `AI` 的分子就是这个"道数"。

`FMA`（乘加融合）一条指令干了两件事：`a*b+c`。业界惯例算 **2 FLOP**
（这样才和"每通道每周期 2 FLOP"的硬件口径对齐）。你要是按指令条数数，
`AI` 直接减半，点在横轴上左移一半，看着像"离屋顶更远了"——其实只是换了尺子。
`half2` 同理，一条指令算两个 fp16。

本机还有一个坑：fp16 实测 0.32 TFLOP/s，比 fp32（2.76）慢 8.6 倍。
如果还拿"打包翻倍"的理论去数它的 FLOP，屋顶就是**假的**
（本机没有 Tensor Core，任何"TC 峰值"的屋顶都不存在，见 `README.md` 约束一）。

**规矩：一个项目里定死一套计数规则并写进报告。** 本项目按业界惯例
**FMA = 2 FLOP**。规则不统一，跨 kernel 比较 `AI` 就没有意义。

### 汇总

| 盲区 | 症状 | 怎么查 |
|---|---|---|
| 1. 屋顶是理想值 | 点远在屋顶下方 | ncu 看 stall 原因和 MLP，区分"延迟"还是"资源不够" |
| 2. `bytes` 指哪一级 | 看着该到算力屋顶却到不了 | 分层画 L1 / L2 / DRAM 三条屋脊，取最低 |
| 3. 口径混用 | 两个百分数互相打架 | 瓶颈用 ncu 同源指标比，优化空间用 roofline 口径算 |
| 4. FLOP 计数不定 | 点莫名平移 2~4 倍 | 固定 FMA = 2 FLOP，并在报告里写明 |

> **roofline 负责指方向，ncu 负责指距离，而尺子必须两边统一。**

## 8. 怎么自己重算 / 加一条新屋顶

```powershell
python phase0/calibrate.py     # 重新标定 P 和 B（屋顶的高度）
python phase0/roofline.py      # 重画 roofline.png，会自动读 measured/*.json
```

手工算一个 kernel 只需要三个数：

```text
AI   = 这个 kernel 的 FLOP 数 / 它搬的字节数
屋顶 = min(算力峰值 P, AI * 带宽峰值 B)
利用率 = 实测性能 / 屋顶
```

要**加一个数据点**：往 `phase0/measured/<名字>.json` 的 `points[]` 里加
`{name, ms, gflops, gbps, ai}`，再跑一次 `roofline.py`（纯访存 kernel 的
`gflops` 可以写 0，脚本会用 `gbps * ai` 反推）。

要**加一条屋顶线**：改 `roofline.py` 的 `main()`。
比如阶段 1 之后想画 fp16 的算力屋顶，把 `peak_gflops` 那几行换成
`hw["matmul"]["fp16"]["tflops"]` 再叠一条线即可。

| memory-bound | 带宽受限 | 卡在装卸口，工作台闲着 |
| compute-bound | 算力受限 | 卡在工作台，料在门口排队 |
| ridge point | 转折点 / 屋脊点 | 两条屋顶线的交点，= `P / B` |
| machine balance | 机器平衡点 | 数值上等于转折点，本机 15.4 FLOP/byte |
| lower / upper bound | 下界 / 上界 | 时间有下界 => 性能有上界，方向别记反 |
| peak / attainable | 峰值 / 可达值 | 屋顶高度 / 实际能跑到的位置 |

---

## 一句话收束

> **能跑多高由屋顶封顶，跑得多低由你自己的实现决定。**

## 10. 实例：点没贴到屋顶，先问"屋顶画的是哪一级"（2026-10-03 补）

`cache_probe` 实验的四个点里，有三个（64KB / 256KB / 1MB）远在红色算力屋顶下方，
只有 2 % 左右——**看起来像"优化空间巨大"，其实是屋顶画错了层级。**

这三个点的复用距离都远小于 1 MB，数据全部由 **L2** 服务（L2 命中 99 %+），
DRAM 几乎没参与。而图上的 AI 用的是 **DRAM 口径**：分子（FLOP）不变，
分母（DRAM 字节）被压到只剩义务流量，于是 AI 被推到 20 ~ 364，落进"算力区"。

**但"落在算力区"只说明"DRAM 不再限制你"，不说明你被算力卡住。**
那三个点实测的 SM 利用率只有 19 ~ 25 %，根本没碰到算力屋顶。

换成 L2 口径重算（`AI_L2 = FLOP / L2 字节`，L2 速率取实测约 285 GB/s）：

| 档 | DRAM 口径 AI | 对红色算力屋顶 | **L2 口径 AI** | **对 L2 屋顶** |
|---|---|---|---|---|
| 64KB | 364.2 | 2.1 % | 0.250 | **80 %** |
| 256KB | 81.7 | 2.4 % | 0.250 | **93 %** |
| 1MB | 20.4 | 2.6 % | 0.250 | **~101 %** |
| 64MB | 0.333 | — | 数据本来就走 DRAM | DRAM 屋顶 87 % |

**换成正确的层级后，三个点立刻贴上屋顶。**

> 第三个略微超过 100 %，说明 L2 速率取 285 GB/s 略保守（真实值可能在 290 以上），
> 也说明 L2 的"屋顶"不是严格平的——它会随访问模式变化。

这正是**盲区 2** 的实例：AI 的分子分母必须用**同一级**的字节数。
用 DRAM 口径画图、却拿算力屋顶去衡量一个 L2 受限的 kernel，
会得出"离屋顶很远"的假象。

### 图已经改成双面板了（2026-10-03）

`reports/roofline.png` 现在是两张并排的图，**同一批点、两把尺子**：

| 面板 | 横轴 | 屋顶 | 三个缓存点在哪 |
|---|---|---|---|
| (a) 左 | FLOP / **DRAM** byte | 179 GB/s | 散在右边、远低于红线（看着像没优化） |
| (b) 右 | FLOP / **L2** byte | 289 GB/s（实测值） | **挤在 0.25 处、正好贴着蓝线** |

实现要点（`roofline.py`）：

- `measured/*.json` 新增 `dram_bytes` / `l2_bytes` 两个字段（由 ncu 实测回填）
- `ai_l2 = ai_dram x dram_bytes / l2_bytes`（同一个 FLOP 分子换算）
- L2 速率放在 `hardware.json` 的 `cache.l2_gbps`；取不到时脚本回退到 289

> (b) 面板的屋顶是**实测经验值**（`cache_probe` 里最好的那档），不是厂商标称。
> 它与访问模式有关，换个 kernel 可能略有不同。
> 另外注意：重跑 `calibrate.py` 会重写 `hardware.json`、丢掉 `cache` 字段，
> 此时 `roofline.py` 用回退值，不影响出图。

### 怎么判断该用哪一级

```text
看 ncu 的 GPU Speed Of Light：
  DRAM Throughput 最高  ->  用 DRAM 口径（标准 roofline 就够）
  L2 / L1 吞吐最高      ->  需要分层 roofline，按那一级重算 AI
  都不高、SM 也不高     ->  不是吞吐问题，是延迟问题（roofline 帮不上）
```
