# 概念笔记 01 · 访存、SM 利用率、合并、在途请求

给初学的自己。四个概念，每个配一个比喻。

---

## 0. 先纠正一个前提

你说："SM 不是一直有活儿干嘛，只是算得快，占的时间少而已。"

**前半句对，后半句反了。** 看 ncu 实测的这三个数（vecadd，block=128）：

| 指标 | 值 | 含义 |
|---|---|---|
| Active Warps Per Scheduler | **7.60 / 8** | SM 上塞满了 warp，活儿管够 |
| Eligible Warps Per Scheduler | **0.03** | 但同一瞬间，几乎没有 warp 能干活 |
| No Eligible | **97.16 %** | 97% 的周期里，调度器找不到任何可发射的指令 |
| Warp Cycles Per Issued Instruction | 267.71 | 每个 warp 发一条指令平均要等 268 个周期 |
| 其中等内存（L1TEX scoreboard） | 238.4 周期 = **89.1 %** | 等待几乎全来自访存 |

**比喻**：8 个厨师站在灶台前，每人面前都有一张单子（活儿管够），
但冰箱在 500 米外，取一趟料要 500 个周期。
于是 97% 的时间里，8 个厨师全都卡在等料上，没人能下锅。

他们不是"干得快所以闲"，是**卡住了**。

## 1. 访存的"最小包装"和"对齐"

内存不是想拿多少拿多少。GPU 只给你三种规格的箱子：

| 箱子 | 指令 | 一次拿多少 |
|---|---|---|
| 小箱 | LDG.32 | 4 字节 |
| 中箱 | LDG.64 | 8 字节 |
| 大箱 | LDG.128 | 16 字节 |

- `float4` = 16 字节，**正好有对应的箱子**，一条指令装完
- `float3` = 12 字节，**没有 12 字节的箱子**，只能拿 3 个小箱，发 3 条指令

再加上"对齐"这个约束：箱子必须放在整格的位置。

数组 `float3 a[N]` 里第 i 个元素在字节偏移 `12 * i` 处：

| i | 偏移 | 16 字节对齐? |
|---|---|---|
| 0 | 0 | 是 |
| 1 | 12 | 否 |
| 2 | 24 | 否 |
| 3 | 36 | 否 |
| 4 | 48 | 是 |

**4 个元素里只有 1 个落在整格上。** 硬件根本没法保证它对齐，
所以连"用大箱装一部分"都做不到，只能退回 3 条 4 字节的指令。

一句话：**float4 天生对齐、天生有箱子；float3 天生不对齐、天生没箱子。**

## 2. SM 利用率：不是"干得快"，是"卡住了"

"Compute (SM) Throughput = 4.98%" 指的是：
**在整个 kernel 的运行时间里，SM 的算术管线只有 4.98% 的周期在干活。**

这个数低有两种截然不同的原因：

- (a) 算得太快，活儿一会儿就干完了 → 那总时间应该很短
- (b) 算不了，在等别的资源 → 那总时间被别的资源拖住

vecadd 是 (b)。**证据**：kernel 跑了 4.5 ms。
如果计算是瓶颈，它应该只花 `4.5 ms x 4.98% = 0.22 ms`。
多出来的 4.3 ms 全部花在等数据上。

**推论：把计算速度提高 10 倍，总时间几乎不会变。**

比喻：你在餐厅等外卖，吃饭只要 5 分钟，但外卖 45 分钟才到，总共 50 分钟。
你把吃饭速度提升一倍，总时间从 50 变成 47.5 分钟。
这就是"优化算力收益为 0"的确切含义。

**注意**：SM 里有很多种单元，别把它们混为一谈。

| 单元 | vecadd 的忙碌度 |
|---|---|
| 算术管线 Compute (SM) | 4.98 % |
| 访存管线 Mem Busy | 56.34 % |
| **DRAM** | **93.31 %** |

真正忙的是 DRAM。SM 在忙着"发访存请求 + 等结果"，不是在算数。

## 3. coalesced（合并访存）

**背景**：一个 warp = 32 个线程，它们**手拉手一起**执行同一条访存指令。
硬件会把这 32 个地址**看一遍**，再决定去内存拿几块。

**最小格子**：内存搬运的最小单位是 **32 字节一个 sector**。
只要你碰了某个 sector 里的任何 1 个字节，**整个 32 字节都会被搬回来**。

**比喻：32 个人同时点外卖**

- **合并**：32 个人的地址是连着的。线程 0 要 a[0]、线程 1 要 a[1]……
  线程 31 要 a[31] → 连续 128 字节。后厨一看是同一片区域的菜，
  **一趟全端出来**，128 字节全部有用。
- **不合并**：线程 0 要 a[0]、线程 1 要 a[1024]、线程 2 要 a[2048]……
  地址散落在 32 个角落。后厨要跑 **32 趟**，每趟只用到 4 字节，
  剩下 28 字节白搬。带宽浪费 8 倍。

回到 float3：线程 i 读 `a[i]`，地址是 `12 * i`，
32 个线程覆盖 `0 ~ 383` 这 **384 个连续字节**。

编译器把它拆成 3 条指令：
- 第 1 条拿 .x（偏移 0, 12, 24, ...）
- 第 2 条拿 .y（偏移 4, 16, 28, ...）
- 第 3 条拿 .z（偏移 8, 20, 32, ...）

三条加起来，**384 个字节一个不漏地全被覆盖**。
从 DRAM 角度看，搬 384 字节对应 384 字节有用数据 —— **零浪费**。

**多跑腿，但没多搬货。而 DRAM 只在乎搬了多少货。**

对比：如果地址是跳跃的，那是"多跑腿 + 每趟空载一半"，那才叫浪费。

> 结论：coalesced 关心的是 **字节有没有被浪费**（DRAM 层面）；
> 指令数关心的是 **花了几条指令**（SM 层面）。
> float3 让后者变差，没让前者变差。瓶颈在 DRAM，所以看不出代价。

## 4. 在途请求 与 Little's Law

**问题**：为什么 14 个 block（每 SM 一个）就能打满带宽？

**比喻：外卖骑手**

- **延迟** = 骑手出发、送达、再回来，要 500 ns
- **带宽** = 你希望每秒送出多少货

只派 1 个骑手：出去、500 ns 后回来、再派下一个。
吞吐 = 一趟的货 / 500 ns。慢得可怜，瓶颈是"骑手太少"。

同时派 100 个骑手：有人回来时还有人在路上，路上的货一直不断。
吞吐 ≈ 100 x 一趟的货 / 500 ns。瓶颈变成了"餐厅出餐速度"（= DRAM 带宽）。

**Little's Law**：

    在途数量 = 吞吐量 x 延迟

要维持 179 GB/s、延迟约 600 ns：

    在途数据 = 179e9 B/s x 600e-9 s ≈ 107 KB

**只要有约 107 KB 的数据同时在路上，带宽就打满了。**
至于这 107 KB 是 14 个 block 凑的还是 16384 个 block 凑的，**完全无所谓**。

我们的情况：14 个 block = 112 个 warp，每个 warp 一次 float4 访存 = 32 x 16 = 512 字节，
一轮就是 57 KB。再叠加编译器让每个 warp 同时挂多个未完成请求（循环流水），
107 KB 轻松达到。**所以 14 个 block 就够了。**

**再加更多 block 会怎样？**

比喻：**高速公路收费站**。车少时收费口空转（带宽没用满）；
车多到一定程度后，**所有收费口都满负荷，再多的车只是排队，通过量不变**。

这就是曲线从 14 涨到 16384 只差 0.8% 的原因 —— 早就过了饱和点，
后面多出来的 1000 倍并行度全在排队。

**正确的说法不是**"每个 SM 要有充分的活干"，
**而是**"在途访存请求要足够多"。

前者问的是"分配了多少任务给你"，后者问的是"此刻有多少请求真的在路上"。
饱和之后，加任务不再提高吞吐。

## 5. 四条串起来

> GPU 的性能由**瓶颈资源**决定。瓶颈一旦饱和，
> 其他所有资源的优化收益都是 0 —— 连更差的写法也看不出代价。

vecadd 里瓶颈是 DRAM（93.31%），其余全是闲置或阻塞的：
算术管线 4.98%、调度器 97% 的时间找不到能干的 warp。
指令数、向量宽度、block size 怎么变，DRAM 一口也吃不下更多。

**实操判断方法**：拿到 kernel 第一件事，看 ncu 的
`DRAM Throughput` 和 `Compute (SM) Throughput` 谁高。
谁高谁就是瓶颈，就优化谁；另一个怎么折腾都没用。
