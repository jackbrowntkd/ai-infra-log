# 笔记 04 · 向量加的执行流程：从一行 CUDA 到 448 个班组轮 4681 次班

这篇只讲一件事：**`c = a + b` 这行代码，在你的 T600 上究竟是怎么跑完的。**
不用新概念，把 `03` 里的零件按时间顺序串一遍。

所有数字都是本机实测，出处标在最后一节。

---

## 0. 这次的活（真实参数）

| 项 | 值 |
|---|---|
| a / b / c | 各 64M 个 float = 各 **256 MB** |
| 一次启动总搬运量 | **768 MB**（读 a + 读 b + 写 c） |
| kernel | `vecadd_naive`（一个线程处理一个元素） |
| block | **256** 线程 |
| grid | **262144** 个 block（= 64M / 256） |

为什么选 naive 而不是 float4 来讲：naive 里 **"第 i 号工人处理第 i 个元素"** 是严格 1:1，
映射关系最干净，不会掩盖任何细节。

---

## 1. 你写的：编程模型（全是纸面上的）

```
grid  = 262144 个 block
  └── block = 256 个 thread
        └── thread = 干 a[i] + b[i]
```

代码里只有一行在回答"我是谁":

```cuda
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) c[i] = a[i] + b[i];
```

**具体举个例**：第 `100` 号 block 里的第 `7` 号工人

```
i = 100 x 256 + 7 = 25607
```

他负责：

```
读 a[25607]  ->  a 的首地址 + 25607 x 4 字节
读 b[25607]
写 c[25607]
```

注意 `blockIdx` / `blockDim` / `threadIdx` 是 **CUDA 提供的"虚拟坐标"**，
硬件上并不存在这三个数，它们由芯片在启动时喂进来。

---

## 2. 硬件上真实存在的东西（关键落差）

纸面上你要 **6710 万个工人**。但硬件真身只有这么多：

| 真实硬件 | 数量 |
|---|---|
| 车间（SM） | **14 个** |
| 每个车间能同时住的班组（warp，32 人一组） | **32 个** |
| **合计同时在场** | **448 个班组 = 14336 个工人** |

而软件要求的是：`262144 个 block x 8 个班组 = 2097152 个班组`。

```
2097152 / 448 = 4681.14
```

**这就是"波（wave）"**：硬件住不下，得**轮 4681 次班**。

> ncu 里有个指标就叫 `Waves Per SM`。
> float4 版实测 **1170.29**，手算 `524288 / 448 = 1170.3`，完全吻合。

---

## 3. 一次换班里发生什么（镜头对准 1 个 block）

- 一个 block = 256 线程 = **8 个班组**，被**整体**安置进某一个车间；
- 车间把这 8 个班组平均分给 4 个工位组（SMSP），每组 2 个；
- **block 不会被拆到两个车间**，它是不可分割的安置单位。

车间住满（4 个 block = 32 个班组 = 1024 线程）就不再收人，
等人干完搬走，再放新 block 进来。这就是那 4681 轮的来源。

**车间为什么正好住 4 个 block？** 本机寄存器 18 格/线程，算下来：

```
65536 格 / (18 格 x 256 线程) = 14.2 个 block    <- 寄存器不是瓶颈
线程上限 1024 / 256 = 4 个 block                 <- 这个才是瓶颈
```

所以理论占用率 100%，实测 `Achieved Occupancy 94.21%`。

---

## 4. 再拉近：一个班组执行一条指令

班组 0 = 线程 0..31，他们算出的 `i` 是 `0..31`。

班长（warp scheduler）发一条"去取货"：

```
LDG R3, [R2]      ; 32 个工人同时报地址: a[0], a[1], ... a[31]
```

这 32 个地址**连续**，每个 4 字节，合计正好：

```
32 x 4 = 128 字节 = 一整块 cache line = 4 个 32 字节的 sector
```

硬件一看"都在同一块砖里" -> **一辆车拉回来**。这就是**合并访存**。

> 反例：如果 32 个工人要的货散落在 32 个不同的砖里，
> 同样一条指令就要发 **32 辆车**。带宽利用率直接掉到 1/32。

---

## 5. 货从哪里来（真实路径）

```
DRAM     ->     L2     ->     L1     ->   寄存器   ->   工作台   ->   写回
厂外大仓库    厂区中转仓    车间货架     手里托盘      FADD        STG
  4 GB         1 MB        96 KB*      18 格/线程
                            (* 与 shared memory 共用)
```

跑腿的（LD/ST）把取货单交出去后，**这个班组就卡住了**。实测平均要等：

```
Warp Cycles Per Issued Instruction = 267.71 周期
其中 238.4 周期（89.1%）在等内存
```

---

## 6. 那为什么还这么快？—— 448 个班组轮着上

班长**不等货**。它把班组 A 的取货单交出去，立刻转头问班组 B、C、D 有没有活干。
这个"换班"机制就是 GPU 掩盖内存延迟的全部秘密。

ncu 实测这个机制的压力：

| 指标 | 实测 | 意思 |
|---|---|---|
| Active Warps Per Scheduler | 7.60 / 8 | 班长手上**班组满了** |
| Eligible Warps Per Scheduler | 0.03 | 但平均只有 0.03 个**真的能干活** |
| No Eligible | **97.16%** | 97% 的时刻，**一个能干的都没有**（全在等货） |
| DRAM Throughput | **93.31%** | 可仓库门口**忙到 93%** |

**能跑满，不是因为工人算得快，是因为"在途的取货单"足够多。**

> 这正是之前"grid = 14 就打满"的原因：
> 需要的不是"活多"，而是**同时在途的访存请求够多**（memory-level parallelism）。

---

## 7. 总账

| 量 | 值 |
|---|---|
| 纸面工人数 | 6710 万 |
| 真实同时在场 | 14336 |
| 轮班次数 | 4681 波 |
| 总搬运量 | 768 MB |
| 耗时 | **4.54 ms** |
| 带宽 | **177 GB/s**（纸面峰值 192） |
| DRAM 利用率 | 93.31% |
| **计算单元利用率** | **4.98%** |

**一句话：**

> 加法本身是零成本的。整件事就是"**把 768 MB 从厂外仓库搬进车间，再搬回去**"。
> 工作台（FP32）全程 95% 的时间闲着，累死的是跑腿的（LD/ST）和仓库门口（DRAM）。

这也解释了之前所有"反常"结果：

- **block 从 256 调到 1024 没区别**：反正都是在等货，工人多几个少几个无所谓；
- **grid 小到 14 就打满**：4681 波压成 1 波也够喂饱 DRAM；
- **float3（指令数翻三倍）不变慢**：多出来的 load 指令被 95% 的空闲发射能力吸收了。

**复现命令：**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File phase0\cuda\build.ps1 phase0\cuda\vecadd.cu
.\phase0\cuda\vecadd.exe
ncu --set full -k "regex:vecadd_float4" --launch-skip 20 --launch-count 1 .\phase0\cuda\vecadd.exe
```

> 注：上面 ncu 那几行计数器是对 `vecadd_float4`（block=128, grid=131072）采的，
> 它的 `Waves Per SM = 1170.29` 和本文 naive 版的 4681 是同一个算法的两个配置。
> 两者实测耗时只差 1.3%（4.480 vs 4.539 ms），结论完全通用。
