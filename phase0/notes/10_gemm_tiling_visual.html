GEMM 四个版本
是怎么一点点变快的

四个版本算的是同一件事：C = A × B。
差别只有一句：同一份数据，被搬了几遍。

v0 naive
各搬各的
v1 tiled
换位置 · 加货架
v2 reg
换次数 · 一次多拿
v3 reg2
换方式 · 排好队形

先看一个画面

算 C 的一个格子，要把它左边那一整行和上面那一整列对齐了相乘再相加。 这没问题。问题出在算第二个格子的时候——

后面四个版本，全都只在解决这一件事。
v1 想办法别搬第二遍，v2 想办法一次多拿点。就这样而已。

先认几个角色（沿用笔记 03 的工厂比喻）

🏭 厂外大仓库显存 DRAM4 GB，远，一趟 500 步
📦 厂区中转仓L2 缓存1 MB，自动管
🧰 车间货架共享内存 shared memory每个车间 64 KB，程序自己管
🫴 工人手上的托盘寄存器每个车间 64 KB，最快，伸手就有
🏃 跑腿的LD/ST 单元（LSU）人数固定，取一次数占一个
🔨 工作台FP32 运算通道896 个，真正做乘加的地方

记住一条就够：跑腿的人数是固定的。取数指令一多，他们立刻成为瓶颈。

v0

naive

把定义直接抄成代码，谁要料谁自己去仓库拿
// 一个工人 = 一个 C 格子，从头算到尾
float acc = 0.f;
for (int k = 0; k < N; ++k)
    acc += A[row * N + k] * B[k * N + col];   // 每次都要取 2 个数
C[row * N + col] = acc;
只改了这一件事
这是基准，什么都没改。先跑出一个能对上答案的正确版本，后面每一步都跟它比。

v1

tiled

在车间里放一个货架：跑一趟仓库，全班一起用
__shared__ float As[32][32], Bs[32][32];   // 车间货架

for (int t = 0; t < 32; ++t) {
    As[ty][tx] = A[row * N + t*32 + tx];   // 全班 1024 人，每人搬 1 个
    Bs[ty][tx] = B[(t*32+ty) * N + col];  // —— 一趟就搬完 32×32
    __syncthreads();                        // 等大家搬完

    for (int k = 0; k < 32; ++k)
        acc += As[ty][k] * Bs[k][tx];       // 从货架拿，不是仓库
    __syncthreads();
}
只改了这一件事
换了个地方放料 —— 从"各自去仓库"改成"先搬到车间货架，全班共用"。
取数的次数没变，变的是取数的距离。

还是它，只是轻了点
才快 1.40 倍？因为仓库本来就没被累到——车间里那个自动货架（L1 缓存）早就在偷偷帮你接住重复取料了， 命中率 94.9%。所以 v1 省下的不是"跑仓库的次数"，而是"跑腿的在车间里来回搬的次数"。
这也是本页最想让人记住的一条：算出来"要搬 32 遍"不等于"仓库真的搬了 32 遍"—— 中间隔着一层缓存。想知道物理上到底搬了几次，只能看计数器。
新的麻烦：跑腿的（71.9%）依然是最忙的那个。货架加得再大也没用——
→ 下一步：减少取数的"次数"本身。
v2

tiled + reg

一次从货架抱 8 个回去，攒够 16 个活儿再跑一趟
float acc[4][4];                          // 手上一次端 16 个格子

for (int k = 0; k < 16; ++k) {
    float aReg[4], bReg[4];
    for (i) aReg[i] = As[k][ty*4 + i];      // 取 4 个
    for (j) bReg[j] = Bs[k][tx*4 + j];      // 取 4 个
    // —— 一共只跑 8 趟腿，却做出 16 个乘加：
    for (i) for (j) acc[i][j] += aReg[i] * bReg[j];   // ★ 16 次乘加
}
只改了这一件事
让每个工人手上一次端 16 个格子。
料从哪来没变（还是货架），变的是每跑一趟腿能干多少活。

v3

tiled + reg2

不搬得更少，而是把取料的队形排对 —— 照 ncu 官方 rules 改
这一步的转折：官方 diagnostics 推翻了我们的方向。
v2 之后最忙的是货架（97.3%），看起来该"再取少一点"。但 ncu --set full 给出的第一条建议是： 
OPT  Est. Speedup: 59.93%  全局 load 访存模式差：
                   每个 32 字节的 sector，每线程只用到 7.1 字节
OPT  Est. Speedup: 57.79%  全局 store 同样差：只用到 8.0 字节
OPT  Est. Speedup: 48.19%  每个 warp 平均花 19.7 周期等 MIO 指令队列
问题不是"取得太频繁"，是每次取都在浪费——跑腿的拉回来 32 字节，只用得上 7 个。 
// 三处改动，全是"队形"问题，没有一处是"少取几次"

// ① 全局 load：原来 warp 内 32 个线程读 32 个不同的行（步长 N）
//    → 换成连续线程读连续的 k
As[c][r] = A[(size_t)(rowStart + r) * N + t + c];   // 合并 ✓

// ② 全局 store：原来按 tx*4 跨步写，每个 sector 只用 8/32 字节
*reinterpret_cast<float4*>(&C[...]) = v;              // 一次写 16 B ✓

// ③ 共享内存取数：一条 float4 顶 4 条 → MIO 队列压力降下来
float4 a4 = *reinterpret_cast<const float4*>(&As[k][ty*4]);
只改了这一件事
换的是取数的"方式"，不是次数：
让 32 个工人要的数据在内存里挨着，一趟拉齐、一趟写齐、一条指令取 4 个。

官方估 60%，实际拿到 45%（3.696 → 2.036 ms，+82%）。三条指路全部应验： 访存告警消失、MIO 等待从 19.7 周期降到 7.1、发射间隔 5.3 → 2.7 周期。

新的麻烦：这次官方指着货架本身了——共享内存 store 有 1.5 路 bank conflict（524288 次），而且每 2.7 周期才发得出一条指令。
→ 下一步：消除货架上的碰撞。
v4

消除 bank conflict + 一次端 64 个

官方已经指名了下一个目标 —— 还未实现

v3 之后 ncu --set full 给的新指路：

OPT  Est. Speedup: 31.57%  共享内存 store 有 1.5 路 bank conflict（524288 次）
OPT  Est. Local Speedup: 47.53%  每 2.7 周期才发得出一条指令
OPT  Est. Speedup: 44.78%  warp 仍在等 MIO 队列（7.1 周期）
方向做法为什么
消冲突调整 As/Bs 的行距或索引映射 同样一趟腿，别让两个工人抢同一个货架格
再摊薄每个工人端 8×8 = 64 个（现在 4×4=16） 取 16 个 → 做 64 次乘加，比例 0.5:1 → 0.25:1
目标：把工作台（现在 54.4%）推到真正的天花板。 离峰值 38.2% 还远——远没收敛。

附录 · 那个 S 是什么

sgemm = Single · GEneral · Matrix-Multiply，是 BLAS 的命名法，每位回答一个问题：

位置回答什么取值
S什么类型S=fp32 · D=fp64 · C=复数单 · Z=复数双
GE矩阵结构GE=一般矩阵（不假定对称/三角/带状）
MM做什么运算MM=矩阵×矩阵

只加一个字母就换一家：dgemm 双精度、sgemv 矩阵×向量、symm 对称矩阵×矩阵。
两个常问的点：为什么只有一个字母——Fortran 77 标识符上限 6 个字符，SGEMM 正好 6 个； 为什么 Z 不是复数双的 C——C 被单精度复数占了，双精度复数只能用没被占的 Z。
⚠️ 别外推到半精度：netlib BLAS 里没有 fp16，cublasHgemm 的 H 是厂商后来加的。
